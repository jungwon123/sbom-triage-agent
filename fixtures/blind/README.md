# 블라인드 테스트 세트

파이프라인을 만든 쪽과 독립적으로 준비한 입력과 정답이다. 이 프로젝트의 점수 규칙, 에이전트 코드, 기존 정답 라벨은 보지 않고 만들었다. 파이프라인을 돌리는 쪽은 `answers.csv`를 열지 않고 SBOM 두 개만 입력으로 쓴다.

| 파일 | 내용 |
|---|---|
| `sbom-a.cdx.json` | CycloneDX 1.5 JSON, npm 컴포넌트 40개 |
| `sbom-b.spdx.json` | SPDX 2.3 JSON, PyPI 패키지 40개 (루트 패키지 별도) |
| `answers.csv` | 정답 라벨. 열은 `sbom,package,version,cve,ghsa,label,reason` |

## SBOM A: storefront-order-api (npm)

- 가상의 쇼핑몰 주문·회원 API다. Express 서버가 JSON API와 서버 렌더링(EJS) 관리 화면을 함께 제공하고, 관리 화면은 jQuery를 브라우저로 내려보낸다.
- **인터넷에 노출된다.** 로그인 전 요청도 받으며 파일 업로드(multipart)와 웹소켓 엔드포인트가 있다. 서비스 중요도는 높다(주문, 회원 정보).
- 직접 의존성과 전이 의존성은 `dependencies`로 구분한다. 루트(`metadata.component`)의 `dependsOn`에 있는 것이 직접 의존성이다.
- 개발·빌드 전용 패키지는 `scope: "optional"`과 `cdx:npm:package:development=true` 속성으로 표시했다. 운영 배포본에는 실리지 않는다.

## SBOM B: docflow-backoffice (PyPI)

- 가상의 사내 문서 처리·리포트 백오피스다. Django API와 Celery 워커로 이루어져 있고, 직원이 올린 이미지·YAML·엑셀을 처리해 PDF 리포트를 만들며 SFTP로 사내 시스템에 전달한다.
- **인터넷에 노출되지 않는다.** 사내망에서 로그인한 직원만 접근한다. 서비스 중요도는 중간이다.
- 직접 의존성은 루트 패키지에서 나가는 `DEPENDS_ON`, 전이 의존성은 패키지 사이의 `DEPENDS_ON`으로 표현했다.
- 개발·빌드·테스트 전용 패키지는 `DEV_DEPENDENCY_OF`, `BUILD_DEPENDENCY_OF`, `TEST_DEPENDENCY_OF` 관계로 루트에 연결했다(루트의 `DEPENDS_ON`에는 없다).
- purl은 각 패키지의 `externalRefs`(`PACKAGE-MANAGER` / `purl`)에 있다.

## 패키지를 고른 방법

- 전부 실제로 배포된 패키지와 버전이다. 2026-11-18에 OSV(`api.osv.dev`)에 purl로 조회해 취약점이 반환되는지, 취약점이 없는 패키지는 0건인지 확인했다.
- 난이도를 일부러 섞었다.
  - CISA KEV에 등재된 취약점
  - 점수는 높지만 악용 근거가 약한 취약점
  - 점수는 낮거나 중간인데 EPSS가 높은 취약점
  - 낮은 심각도 취약점
  - 점수가 높은 개발·빌드 전용 패키지
  - 취약한 전이 의존성
  - 수정 버전이 없는 패키지
  - 알려진 취약점이 없는 패키지
- 한 패키지에 취약점이 여러 건인 경우가 많다. 정답은 그중 근거가 분명한 일부에만 매겼으므로, 정답에 없는 취약점은 채점 대상이 아니다.
- PyPI는 OSV가 같은 CVE를 `GHSA-…`와 `PYSEC-…` 두 ID로 돌려주는 경우가 있다. 정답은 GHSA ID 기준이며 CVE로도 맞춰 볼 수 있다.
- SBOM은 가상의 서비스를 설명하는 것이라 실제 lockfile의 전체 의존성 트리를 담지는 않는다.

## 라벨 기준

라벨은 취약점 한 건 × 패키지 버전 단위다. 근거 자료는 2026-11-17~18 시점의 CISA KEV 목록(카탈로그 2026.11.17), FIRST EPSS, OSV/GitHub 어드바이저리의 심각도와 설명이다.

| 라벨 | 뜻 | 판단 기준 |
|---|---|---|
| NOW | 이번 주에 조치 | 실제 악용 근거(KEV 등재 또는 높은 EPSS)가 있고, 이 서비스에서 공격 경로가 열려 있는 런타임 컴포넌트. 영향이 크고(코드 실행, 데이터 유출, 인증 없는 서비스 중단) 조치가 가벼우면 더 강하게 NOW로 본다 |
| NEXT | 다음 스프린트에 조치 | 런타임에 실리고 심각도가 중간 이상이지만 악용 근거가 약하거나, 앱이 특정 방식으로 써야만 성립하거나, 서비스 노출이 제한적인 경우. 수정 버전이 없어 패키지 교체를 계획해야 하는 런타임 항목도 여기에 둔다 |
| MONITOR | 지켜보고 정기 업데이트 때 처리 | 개발·빌드·테스트 전용, 낮은 심각도, 외부 입력이 닿지 않는 전이 의존성, 전제 조건이 비현실적인 경우 |

판단 순서는 다음과 같다.

1. **악용 근거**: KEV 등재 여부, EPSS 값. EPSS가 높아도 스캐너 탐지나 다른 제품 맥락에서 올라간 값일 수 있으므로 단독으로 NOW를 정하지 않는다.
2. **도달 가능성**: 런타임인가 개발 전용인가, 직접인가 전이인가, 기본 사용 방식에서 공격자 입력이 닿는가.
3. **심각도와 영향**: 점수 자체보다 무엇이 가능한지(코드 실행, 인증 우회, 서비스 거부, 정보 노출)를 본다.
4. **서비스 맥락**: A는 인터넷 노출이라 인증 없는 원격 공격을 무겁게 본다. B는 사내망 전용이라 같은 취약점도 대체로 한 단계 낮게 보되, KEV 등재나 핵심 프레임워크의 치명적 취약점은 낮추지 않는다.
5. **조치 비용**: 패치 버전으로 끝나는지, 메이저 업그레이드나 패키지 교체가 필요한지.

같은 패키지의 여러 취약점이 한 번의 업그레이드로 해결되더라도 라벨은 취약점마다 따로 매겼다.
