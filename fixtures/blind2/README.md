# 블라인드 테스트 세트 2

`fixtures/blind/`에 이은 두 번째 세트다. 같은 사람이 같은 라벨 기준으로 만들었으므로 두 세트의 결과를 나란히 비교할 수 있다. 이 프로젝트의 점수 규칙, 에이전트 코드, 기존 정답 라벨, `out/`은 보지 않고 만들었다. 파이프라인을 돌리는 쪽은 `answers.csv`를 열지 않고 SBOM 두 개만 입력으로 쓴다.

| 파일 | 내용 |
|---|---|
| `sbom-c.cdx.json` | CycloneDX 1.5 JSON, npm 컴포넌트 38개 |
| `sbom-d.spdx.json` | SPDX 2.3 JSON, Maven 패키지 40개 (루트 패키지 별도) |
| `answers.csv` | 정답 라벨. 열은 `sbom,package,version,cve,ghsa,label,reason` |

첫 세트와 겹치는 패키지는 없다(이름 기준).

## SBOM C: settlement-batch-console (npm)

- 가상의 사내 정산 배치·백오피스 콘솔이다. 스케줄러가 정산 배치를 돌리고, Koa로 만든 사내 콘솔에서 직원이 엑셀·이미지·압축 파일을 올리고 리포트를 내려받는다.
- **인터넷에 노출되지 않는다.** 사내망에서 로그인한 직원만 접근한다. 서비스 중요도는 중간이다.
- 리눅스 컨테이너에서 동작한다. 외부 호출은 정해진 사내 API와 SFTP 서버뿐이다. `crypto-js`는 내보내기 파일의 HMAC 서명에만 쓴다.
- 직접 의존성은 루트(`metadata.component`)의 `dependsOn`에 있는 것이다.
- 개발·빌드·테스트 전용 패키지는 `scope: "optional"`과 `cdx:npm:package:development=true` 속성으로 표시했다.

## SBOM D: merchant-settlement-api (Maven)

- 가상의 가맹점 정산 API다. Spring Boot 2.6 실행형 JAR에 내장 Tomcat으로 동작하고, 가맹점이 JSON·XML 요청과 엑셀 파일 업로드를 보낸다.
- **인터넷에 노출된다.** 로그인 전 요청도 받는다. 서비스 중요도는 높다(정산 금액, 가맹점 정보).
- 외부 호출은 고정된 제휴사 주소뿐이다. HTTP Invoker 같은 원격 호출 기능과 H2 콘솔은 쓰지 않는다.
- 직접 의존성은 루트 패키지에서 나가는 `DEPENDS_ON`, 전이 의존성은 패키지 사이의 `DEPENDS_ON`이다.
- 테스트 전용 패키지는 `TEST_DEPENDENCY_OF`, 개발·빌드 전용 패키지는 `DEV_DEPENDENCY_OF` 관계로 루트에 연결했다(루트의 `DEPENDS_ON`에는 없다).
- purl은 각 패키지의 `externalRefs`에 `pkg:maven/group/artifact@version` 형태로 있다. 패키지 `name`과 `answers.csv`의 `package` 열은 `group:artifact` 형태다.

## 패키지를 고른 방법

- 전부 실제로 배포된 패키지와 버전이다. 2026-11-18에 OSV(`api.osv.dev`)에 purl로 조회해 취약점이 반환되는지, 취약점이 없는 패키지는 0건인지 확인했다.
- 첫 세트와 같은 종류의 난이도를 섞었다: KEV 등재, 점수는 높지만 악용 근거가 약한 것, 점수는 낮은데 EPSS가 높은 것, 낮은 심각도, 점수가 높은 개발·테스트 전용 패키지, 취약한 전이 의존성, 수정 버전이 없는 패키지, 취약점이 없는 패키지.
- 이번 세트에 새로 넣은 경우는 다음과 같다.
  - 개발 전용 패키지에 KEV 등재 취약점이 있는 경우
  - 테스트 전용 패키지인데 EPSS가 매우 높은 경우
  - OSV 어드바이저리에 CVE 별칭이 없는 경우. 이 행은 `cve` 열이 비어 있고 GHSA로만 맞춰 볼 수 있다
- 한 패키지에 취약점이 여러 건인 경우가 많다. 정답은 그중 근거가 분명한 일부에만 매겼으므로, 정답에 없는 취약점은 채점 대상이 아니다.
- 같은 GHSA가 여러 아티팩트에 걸려 있는 경우(예: Spring 모듈) 정답은 한 아티팩트에만 매겼다.
- SBOM은 가상의 서비스를 설명하는 것이라 실제 빌드의 전체 의존성 트리를 담지는 않는다.

## 라벨 기준

첫 세트와 같다. 라벨은 취약점 한 건 × 패키지 버전 단위이고, 근거 자료는 2026-11-17~18 시점의 CISA KEV 목록(카탈로그 2026.11.17), FIRST EPSS, OSV/GitHub 어드바이저리의 심각도와 설명이다.

| 라벨 | 뜻 | 판단 기준 |
|---|---|---|
| NOW | 이번 주에 조치 | 실제 악용 근거(KEV 등재 또는 높은 EPSS)가 있고, 이 서비스에서 공격 경로가 열려 있는 런타임 컴포넌트. 영향이 크고(코드 실행, 데이터 유출, 인증 없는 서비스 중단) 조치가 가벼우면 더 강하게 NOW로 본다 |
| NEXT | 다음 스프린트에 조치 | 런타임에 실리고 심각도가 중간 이상이지만 악용 근거가 약하거나, 앱이 특정 방식으로 써야만 성립하거나, 서비스 노출이 제한적인 경우. 수정 버전이 없어 패키지 교체를 계획해야 하는 런타임 항목도 여기에 둔다 |
| MONITOR | 지켜보고 정기 업데이트 때 처리 | 개발·빌드·테스트 전용, 낮은 심각도, 외부 입력이 닿지 않는 전이 의존성, 전제 조건이 비현실적인 경우 |

판단 순서도 같다.

1. **악용 근거**: KEV 등재 여부, EPSS 값. EPSS가 높아도 스캐너 탐지나 다른 제품 맥락에서 올라간 값일 수 있으므로 단독으로 NOW를 정하지 않는다.
2. **도달 가능성**: 런타임인가 개발 전용인가, 직접인가 전이인가, 기본 사용 방식에서 공격자 입력이 닿는가.
3. **심각도와 영향**: 점수 자체보다 무엇이 가능한지를 본다.
4. **서비스 맥락**: D는 인터넷 노출이라 인증 없는 원격 공격을 무겁게 본다. C는 사내망 전용이라 같은 취약점도 대체로 한 단계 낮게 보되, 런타임 컴포넌트의 KEV 등재 취약점은 낮추지 않는다.
5. **조치 비용**: 패치 버전으로 끝나는지, 메이저 업그레이드나 패키지 교체가 필요한지.

첫 세트에는 없던 경우에 대한 보충 설명이다.

- 개발·테스트 전용 패키지는 기본적으로 MONITOR다. KEV에 등재된 경우에만 한 단계 올려 본다. EPSS가 높다는 것만으로는 올리지 않는다.
- 런타임 컴포넌트의 KEV 등재 취약점은 이 서비스의 기본 설정에서 전제 조건이 닫혀 있을 수 있어도 낮추지 않았다. SBOM만으로는 설정을 확인할 수 없기 때문이다.
