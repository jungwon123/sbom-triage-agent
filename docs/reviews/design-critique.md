## (a) 가장 심각한 문제 10가지

### 1. 일치율 수치는 정확도의 증거가 되지 못합니다

근거

- 정답 92건은 사람이 아니라 AI 세션이 썼고, 그 라벨 기준이 이 시스템의 점수 항목과 같습니다. `fixtures/blind/README.md`의 판단 순서는 KEV와 EPSS, 런타임 여부와 직접 여부, 심각도, 조치 비용입니다. 같은 특징으로 만든 두 휴리스틱이 서로 얼마나 비슷한지를 잰 것입니다.
- 정답은 "근거가 분명한 일부"에만 매겼습니다(같은 README). 애매한 건이 빠졌으므로 일치율이 실제보다 높게 나옵니다.
- 세 줄짜리 규칙과 비교했습니다. "dev이면 MONITOR, KEV이면 NOW, 나머지는 NEXT"가 92건 중 50건을 맞힙니다. 현재 규칙은 56건, CVSS 정렬은 42건입니다. 세트 2만 보면 세 줄 규칙 24건, 현재 규칙 26건입니다.
- 표본이 작습니다. 56/92의 95% 신뢰구간은 51~70%, 규칙+AI는 58~77%입니다. AI가 고친 것 15건, 틀리게 한 것 8건으로 다시 계산되며 이 차이의 부호 검정 p값은 0.21입니다. "AI가 규칙보다 낫다"는 통계적으로 말할 수 없습니다.
- 지금 `out/`에 저장된 `triage.json`으로 다시 계산하면 규칙+AI는 63/92이고 과소평가는 6건입니다. `HARNESS.md` 132행의 기록은 66/92, 과소평가 4건입니다. 다른 세션의 재실행 때문일 수 있어 원인은 확정하지 못했지만, 발표할 수치가 저장된 결과로 재현되지 않습니다.
- 사람이 매긴 라벨은 12건뿐이고 거기서는 CVSS 정렬 8, 규칙 7, 규칙+AI 4에서 가드 추가 뒤 6입니다(`HARNESS.md` 125~126행). 유일한 사람 기준에서는 규칙이 CVSS 정렬보다 낫지 않았습니다.
- 기존 라벨 20건 중 8건은 도구 결과를 본 AI가 다시 매겼습니다. G20(body-parser 1.20.2, CVE-2024-45590)은 AI가 NOW로 다시 매겼는데, 같은 취약점이고 같은 조건(운영, 직접, 운영 코드에서 import)인 G04는 사람이 NEXT로 매겼습니다(`fixtures/golden-sheet.csv`). 시연의 NOW 4건이 전부 이 body-parser입니다.
- 파라미터 민감도: EPSS 하한, 소스 없음 가중치, 두 임계값을 480가지로 바꿔 보면 세트 2 일치 건수가 11~36건 사이에서 움직입니다. 현재 값(0.8, 0.4, 60, 30)은 26건이고 NEXT 기준을 40으로만 올려도 35~36건이 됩니다. 수치가 임계값 한두 개에 좌우되며 현재 값이 특별히 좋은 자리도 아닙니다. 이 탐색은 정답을 보고 한 것이므로 "이 값으로 바꾸자"는 근거가 아니라 "지금 수치가 얼마나 흔들리는가"의 근거입니다.
- `docs/REQUIREMENTS.md` 342행의 목표는 "에이전트 80% 이상"입니다. 어느 측정에서도 달성하지 못했습니다.

왜 중요한가: 발표의 차별점이 "실측으로 제시"(D25)입니다. 심사위원이 "정답은 누가 매겼습니까"라고 물으면 지금 답은 "다른 AI 세션"입니다.

가장 작은 수정: 발표 전에 사람(가능하면 본인이 아닌 개발자 한 명 포함)이 30~40건을 독립적으로 라벨링합니다. 표에는 세 줄 규칙을 기준선으로 함께 싣고 신뢰구간을 적습니다. 수치를 말할 때는 "AI가 만든 기준과의 일치"라고 명시합니다.

### 2. "NOW 누락 0건"은 설계의 성질이 아닙니다

근거

- 누락의 정의가 "정답 NOW인데 최종 MONITOR"뿐입니다(`backend/triage/eval.py:56`). NOW를 NEXT로 내린 것은 세지 않습니다. 정답 NOW 16건 중 규칙이 NEXT로 본 것이 2건입니다(qs 6.7.0, sharp 0.32.0).
- 정답 NOW 16건은 전부 운영 의존성이고 15건이 KEV이거나 EPSS 백분위 0.969 이상입니다. 라벨 기준이 "악용 근거가 있어야 NOW"이기 때문입니다. 그런 항목은 exploit 점수만으로 20점 이상을 받고 severity가 더해지므로 규칙에서 30점 미만(MONITOR)이 될 수 없습니다. 이 라벨 기준에서는 누락이 생길 수 없게 지표가 짜여 있습니다.
- 규칙은 MONITOR를 거의 주지 않습니다. 92건 중 MONITOR 예측은 18건이고 정답 MONITOR는 47건입니다. 틀린 36건 중 34건이 과대평가입니다. 누락 0건의 상당 부분은 높게 매긴 결과입니다.
- 설계상 누락이 생기는 경로가 두 개 열려 있습니다.
  - 규칙이 MONITOR로 본 항목은 AI가 보지 않습니다(`agent/run.py:236`). AI가 구제할 수 없습니다.
  - AI는 규칙 NEXT를 MONITOR로 내릴 수 있고, 하향 보류(F6-9)는 KEV이거나 "EPSS 0.9 이상이면서 runtime import가 있거나 규칙 버킷이 NOW"일 때만 걸립니다(`score.py:64-72`). SBOM만 있는 입력과 모든 간접 의존성은 `import_sites`가 항상 비어 있으므로(`scan.py:114`) 규칙 NEXT 항목에는 보류가 걸리지 않습니다. 재현: EPSS 0.99, 간접, SBOM 전용 항목의 `needs_review`는 False입니다.
  - 실제로 일어났습니다. 저장된 결과에서 paramiko CVE-2023-48795(EPSS 백분위 0.998), cryptography CVE-2023-0286(0.993), spring-webmvc CVE-2023-20860(CVSS 9.1, 0.894), mysql2 CVE-2024-21508(CVSS 9.8, 0.853)을 AI가 MONITOR로 내렸습니다. 정답이 NEXT라서 "NOW 누락"으로 세지 않았을 뿐입니다.

코드가 실제로 보장하는 것은 하나입니다. KEV 항목은 규칙에서 MONITOR가 되지 않고 AI가 내릴 수도 없습니다(단, KEV 피드가 최신일 때. 7번 참고).

가장 작은 수정: 보류 조건에서 "runtime import 또는 규칙 NOW"를 빼고 "EPSS 0.9 이상이면 MONITOR로는 내리지 못한다"로 바꿉니다(`score.needs_review` 한 줄). 발표 문구는 "KEV 항목은 구조적으로 MONITOR가 될 수 없고, 92건에서 NOW가 MONITOR로 간 사례는 없었다"로 바꾸고 NOW에서 NEXT로 내려간 건수를 함께 말합니다.

### 4. 도달성 판정이 "못 찾음"을 "안 씀"으로 바꿉니다

근거 (재현 포함)

- 직접 의존성에서 정규식이 import를 못 찾으면 `unused`이고 가중치 0.2입니다(`score.py:29-32`). 못 찾는 경우: 백틱 `require`, 변수로 넘기는 동적 `import(name)`, `require.resolve`, 문자열 설정으로 로드되는 것(`app.set('view engine','ejs')`, ORM이 내부에서 부르는 DB 드라이버, babel, eslint, webpack 플러그인, CLI로만 쓰는 패키지). 전부 빈 결과로 재현했습니다. 블라인드 세트 1의 정답 NOW 1번인 ejs가 바로 이 유형이라, 같은 서비스를 레포로 넣으면 SBOM으로 넣을 때보다 낮게 나옵니다(노출 20점에서 10점).
- 경로 분류: `src/spec/h.js`의 운영 import가 `test`로 분류됩니다(`usages.py:14-15`의 `spec` 디렉터리 규칙). `.mts`, `.cts`는 검색 대상이 아닙니다(`usages.py:16`). `build`, `dist`, `out`, `vendor`, `assets`라는 이름의 디렉터리는 위치와 무관하게 건너뜁니다(`usages.py:18`).
- Maven: groupId를 Java 패키지 접두사로 씁니다(`usages.py:83-86`). `com.google.guava:guava`는 `com.google.guava`(실제는 `com.google.common`), `commons-collections`는 `commons-collections`(실제는 `org.apache.commons.collections`), `log4j:log4j`는 `log4j`, `com.h2database:h2`는 `com.h2database`(실제는 `org.h2`), `tomcat-embed-core`는 `org.apache.tomcat`(실제는 `org.apache.catalina`)입니다. 이 패키지들은 항상 `unused`가 됩니다. 반대로 `org.springframework`는 스프링 모듈 전체에 걸려 전부 import한 것으로 나옵니다.
- 간접 의존성은 import 검색을 하지 않고(`scan.py:114`) 규칙은 항상 `unknown`입니다. 대부분의 취약점이 간접 의존성에 있으므로 "실제 사용 여부" 주장은 LLM의 여섯 번 이내 도구 호출에 전부 걸려 있습니다. `docs/onprem-llm.md`의 비교에서 같은 6건에 대해 두 모델의 판정이 4건 달랐고 로컬 모델은 실행마다 답이 달랐습니다.
- 모노레포: 루트 `package.json`의 의존성만 직접으로 봅니다(`sbom.py:97-99`). 워크스페이스 패키지의 직접 의존성은 간접으로 처리되어 검색하지 않습니다.
- PyPI, Go 등은 검색이 없어 전부 `unknown`이고 0.4를 받습니다. 표시는 정직하지만(`missing`에 `source`) 3번 표의 아래쪽 행들처럼 버킷이 유리하게 고정됩니다.

가장 작은 수정: 직접 의존성 미검출을 `unknown`으로 바꾸고 근거 문장을 "import를 찾지 못했습니다(동적 로드와 설정 로드는 탐지하지 못합니다)"로 바꿉니다. Maven은 접두사 추정을 버리고 "검색 미지원"으로 표시하는 편이 틀린 `unused`보다 안전합니다.

### 5. `verified`가 증명하는 것이 이름보다 훨씬 적습니다

`verified`의 실제 뜻은 "수정된 lockfile에 대상 취약점 id가 없고, 규칙 NOW급 새 취약점이 없고, 조치 전에 통과하던 테스트 이름이 새로 실패하지 않았다"입니다. 다음 경우에도 `verified`가 나옵니다.

- **테스트 전체가 뜨지 못한 경우.** 재현: 기준선이 27개 실행에 1개 실패이고, 조치 후에는 0개 실행에 종료 코드 실패(모듈 로드 오류 등)이면 `verdict()`는 `('verified', 'ok', [])`를 돌려줍니다. 회귀를 "새로 실패한 테스트 이름의 차집합"으로만 계산하고(`verify/run.py:46-50`) 실행 건수가 줄었는지는 보지 않기 때문입니다. 데모 레포는 기준선에서 이미 7건이 실패하는 상태라 이 경로가 실제로 열려 있습니다.
- **테스트가 없는 경우.** `build`, `test` 스크립트가 없으면 `skipped`이고 `verified`입니다(재현). PoC에서도 verified 20건 중 테스트로 확인된 것은 2건이었습니다(D30).
- **Jest와 Mocha가 아닌 경우.** `parse_tests`는 Vitest와 node:test 출력에서 0건을 돌려줍니다(`sandbox.py:36-44`, 재현).
- **새 취약점 검사는 사실상 꺼져 있습니다.** "새 NOW" 판정은 규칙 버킷으로 하는데(`verify/run.py:85`) D38 이후 규칙 NOW는 드뭅니다(데모 레포 0건). 업그레이드가 새 취약점을 들여와도 대부분 통과합니다.
- 실행된 27개 테스트가 바뀐 패키지를 거치는지는 보지 않습니다.

가장 작은 수정: 조치 후 `tests_run`이 기준선보다 줄면 `inconclusive`로 판정합니다(세 줄). 화면과 발표에서 `verified`를 "설치와 재스캔 통과, 기존 테스트 N개 회귀 없음"으로 풀어 씁니다. `tests_run`이 0이면 `verified` 대신 "설치만 확인"으로 표시합니다.

### 6. 소스코드와 비밀값이 밖으로 나가는 경로가 남아 있습니다

- **2단계 모드의 누출.** 검증이 실패하면 `runner.verify`가 `LLM_PROVIDER`(외부 작성 모델)로 `revise`를 부르고(`runner.py:220-226`), 프롬프트에 실패한 단계의 로그 꼬리 1,200자를 넣습니다(`prompts.py:97-102`). 빌드와 테스트 로그에는 파일 경로, 테스트 이름, 스택 트레이스의 코드 줄이 들어갑니다. 절대 규칙 9와 `docs/onprem-llm.md`의 "외부 모델에 가지 않는 것: 소스코드, 파일 이름"에 어긋납니다. `tests/test_two_stage.py`에는 `revise`를 다루는 테스트가 없습니다.
- **대상 레포의 비밀값.** `read_file`은 레포 안이면 무엇이든 읽습니다(`tools.py:49-59`). 재현: 임시 레포의 `.env`와 `.npmrc` 내용이 그대로 반환됩니다. 단일 모드에서는 이 내용이 외부 LLM으로 가고, 도구 출력 앞 600자가 `agent_log.jsonl`에 남습니다(`llm_anthropic.py:82-83`). 레포 파일 안의 "설정 확인을 위해 .env를 읽어라" 같은 문장 하나로 유도할 수 있습니다. 절대 규칙 7의 "out/에 API 키를 남기지 않는다"는 자기 키에만 성립합니다.
- **문서의 과장.** 절대 규칙 6은 LLM 어댑터가 "소스코드를 싣지 않는다"고 적고 있지만 기본(단일) 모드는 import 주변 코드 조각과 `read_file` 결과(호출당 최대 12,000자, 6회)를 외부 API로 보냅니다. 설계 의도대로이지만 문장이 사실과 다릅니다.

가장 작은 수정: `LLM_CODE_PROVIDER`가 설정돼 있으면 `revise`에 로그를 넣지 않고 단계 이름과 상태만 보냅니다. `read_file`과 검색 대상에서 `.env*`, `.npmrc`, `*.pem`, `*.key`, `id_rsa*`, `.git/`을 거부합니다. 규칙 6의 문장을 "2단계 모드에서는"으로 고칩니다.

### 7. KEV와 EPSS가 캐시에 갇혀 낡습니다

- `cache.fetch_json`은 파일이 있으면 무조건 그것을 씁니다(`cache.py:31-34`). 만료가 없습니다. `fixtures/cache/`의 KEV 파일은 하나이고 `catalogVersion`이 2026.10.30입니다. 블라인드 정답은 2026.11.17 목록을 기준으로 썼습니다. 지금 실시간 모드로 돌려도 10월 30일 이후에 등재된 KEV는 보이지 않습니다. EPSS와 OSV 응답도 같은 방식으로 고정됩니다.
- KEV 피드를 받지 못하면 모든 항목이 KEV 아님으로 점수가 매겨집니다(`scan.py:112`). `missing`에 `kev`가 적히지만 버킷은 조용히 내려갑니다. "KEV는 내릴 수 없다"는 유일한 구조적 보장이 피드 상태에 달려 있습니다.
- KEV와 EPSS는 어드바이저리의 첫 번째 CVE 별칭으로만 찾습니다(`scan.py:75`).
- OSV `querybatch`의 `next_page_token`을 처리하지 않습니다(`scan.py:55-65`). 캐시된 125개 응답에는 해당 사례가 없었으나 취약점이 많은 패키지에서 잘립니다.

왜 중요한가: "이번 주에 고칠 것"을 말하는 도구가 3주 전 악용 목록으로 판단합니다. 운영에서 가장 먼저 사고가 나는 지점입니다.

가장 작은 수정: 실시간 모드에서 KEV와 EPSS URL은 하루가 지난 캐시를 다시 받습니다. 실행 결과(`meta.json`)와 화면에 KEV 목록 버전과 EPSS 날짜를 표시합니다. KEV를 받지 못한 실행은 화면 상단에 경고를 띄웁니다.

### 8. 실제 SBOM과 실제 레포에서 조용히 틀립니다

- SPDX 패키지에 purl이 없으면 변환 단계에서 사라지고 `coverage.unsupported`에도 잡히지 않습니다(`sbom.py:277-281`). 재현: purl 없는 lodash 4.17.20이 컴포넌트 목록과 미지원 집계 양쪽에서 빠집니다. "조용히 누락하지 않는다"는 주석과 다릅니다.
- CycloneDX의 `scope: optional`을 dev로 봅니다(`sbom.py:260`). 표준에서 optional은 "실행에 필수는 아님"이지 개발 전용이 아닙니다. 그렇게 표시된 운영 패키지는 가중치 0.2를 받습니다. 블라인드 SBOM은 이 관례에 맞춰 만들어져 있어 문제가 드러나지 않았습니다.
- 의존성 그래프나 루트 컴포넌트가 없는 SBOM은 전부 간접으로 처리됩니다(`sbom.py:261`). Syft가 디렉터리를 스캔해 만든 npm SBOM이 보통 이렇습니다. 그러면 모든 항목의 노출 점수가 14점으로 같아지고, 순위는 CVSS와 EPSS와 KEV의 합이 됩니다. 기존 도구가 이미 주는 정렬입니다.
- SPDX의 `BUILD_DEPENDENCY_OF`는 처리하지 않습니다(`sbom.py:288`). 블라인드 B에 2건 있고 운영으로 분류됩니다.
- 버전 비교가 숫자 세 자리까지만 봅니다(`semver.py:9-19`). 재현: 현재 2.13.4, 수정 2.13.4.2이면 `fixed_in`이 None입니다. jackson-databind가 실제로 이런 버전을 씁니다. 결과는 "수정 버전 없음", effort high, NOW 불가, 조치안은 "완화만"입니다. `rc.9`와 `rc.10`의 순서도 틀립니다.
- `pom.xml`은 직접 의존성만 읽고, 부모 BOM이 버전을 관리하는 의존성은 경고 로그만 남기고 건너뜁니다(`sbom.py:158-163`). Spring Boot 프로젝트의 대부분이 여기에 해당합니다. Syft가 없으면 전이 의존성은 전혀 보이지 않습니다.
- yarn, pnpm, Gradle lockfile은 읽지 못하고, 컨테이너 이미지 SBOM의 OS 패키지(deb, apk, rpm)는 미지원으로 집계만 됩니다.

가장 작은 수정: purl 없는 패키지를 미지원 집계에 넣습니다(한 줄). 그래프가 없는 SBOM이면 "직접 여부를 알 수 없음"을 화면에 경고로 띄웁니다. 네 자리 버전 비교를 고칩니다. `optional`은 `cdx:npm:package:development` 속성이 함께 있을 때만 dev로 봅니다.

### 9. LLM 경계에 남은 틈

성립하는 것부터 적습니다. 점수 필드는 LLM 출력 타입에 없고(`models.py:85-90`), 버킷은 한 단계만 움직이며(`agent/run.py:72-74`), 샌드박스 명령에 들어가는 값은 패턴 검사를 두 번 거칩니다(`apply.py:30-51`, `86-100`). 패키지 이름, 버전, 셸 인용을 여러 방식으로 깨 보려 했으나 명령 주입 경로는 찾지 못했습니다. 이 부분은 주장대로입니다.

남은 틈

- **목표 버전에 상한이 없습니다.** `to_version`은 `fixed_in` 이상이고 형식만 맞으면 통과합니다. 재현: 수정 버전이 1.0.1인 항목에 99.0.0을 제안하면 위반 0건이고 `npm install p@99.0.0`이 만들어집니다. 어드바이저리나 레포 파일의 문장에 유도된 LLM이 임의의 상위 버전(메이저 점프, 문제가 있는 릴리스)을 샌드박스에 설치시키고 "검증된 조치안"으로 화면에 올릴 수 있습니다. `revise`의 "목록에 있는 버전만"은 프롬프트에만 있고 코드 검사가 없습니다.
- **자유 문장 세 곳은 검사하지 않습니다.** `override_reason`, `remediation.mitigation`, `remediation.notes`는 숫자 검사도 내용 검사도 없이 화면에 나갑니다(`agent/run.py:70-81`은 `rationale`만 검사). 재현: `mitigation`에 "curl ... | sh 를 실행하세요"가 그대로 통과합니다. 실행은 사람이 하지만 "코드가 검증한 조치안" 옆에 표시됩니다.
- **자리표시자 규칙은 아라비아 숫자만 막습니다.** "CVSS 구점팔의 치명적 취약점이며 KEV에 등재되어 있습니다", "인증 없이 원격 코드 실행이 가능하며 src/routes/api.js에서 호출합니다"는 위반 0건입니다(재현). 수치가 아닌 사실(KEV 등재, 인증 필요 여부, 어느 파일에서 호출)은 LLM이 지어낼 수 있고 코드가 대조하지 않습니다. "근거는 데이터에서만"은 숫자에 한해서만 참입니다.
- 반대로 `auth0.ts`, `log4j`처럼 숫자가 든 이름은 위반으로 잡힙니다. 계약 위반이 PyPI 20건에 49회, 데모 30건에 첫 답 12회 났고 전부 재호출 비용입니다. 다른 세션이 고치는 중으로 보입니다.
- **SBOM 필드와 서비스 메모.** 컴포넌트 이름과 의존 경로는 SBOM에서 온 문자열 그대로 프롬프트에 들어갑니다. 영향은 한 단계 조정으로 제한되지만 2번의 NEXT에서 MONITOR 경로와 결합하면 "SBOM을 제출한 쪽이 자기 항목을 MONITOR로 보낼 수 있는가"라는 질문이 됩니다. 어드바이저리 본문(D39의 유일한 근거)도 패키지 관리자가 쓰는 글입니다.

가장 작은 수정: `to_version`을 OSV의 수정 버전 목록에 있는 값으로 제한합니다. `mitigation`과 `notes`는 화면에서 "AI가 쓴 제안, 검증되지 않음"으로 구분해 표시합니다. KEV 여부와 파일 이름은 자리표시자(`{kev}`)나 `evidence_files` 대조로만 쓰게 합니다.

### 문제 설정: 기존 도구 대비 무엇이 새로운가

아래 기존 도구 설명은 검토자의 지식 기준이며 오늘 공식 문서로 확인하지 않았습니다. 발표에 쓰기 전에 확인이 필요합니다.

- 세 버킷은 새롭지 않습니다. CISA의 SSVC가 악용 여부, 노출, 영향으로 Track, Attend, Act를 나누는 결정 트리이고 이 시스템의 세 항목과 거의 같은 축입니다. Snyk의 위험 점수도 CVSS, EPSS, 악용 성숙도, 도달성, 수정 가능 여부를 합칩니다. Dependabot은 EPSS 표시, 개발 의존성 자동 분류 규칙, 수정 PR을 제공합니다. OSV-Scanner에는 npm과 Maven의 최소 변경 조치를 계산하는 기능이 있습니다.
- 재구현에 해당하는 것: SBOM에서 OSV 조회, EPSS와 KEV 결합, dev와 prod 구분, 업그레이드 제안. 그래프 없는 SBOM에서는 8번에서 본 대로 CVSS와 EPSS와 KEV의 정렬로 돌아갑니다.
- 상대적으로 새로운 것: (1) LLM의 권한을 타입과 계약 검사로 묶은 구조(점수 필드 없음, 한 단계 조정, 위반 시 규칙으로 대체, 명령은 코드가 조립). (2) 조치 전 기준선과 테스트 이름 단위로 비교하는 샌드박스. (3) 코드 판독 모델과 작성 모델의 분리. 다만 (2)는 Dependabot PR에 레포의 CI가 도는 것과 기능이 겹치고 CI 쪽이 실제 환경에 더 가깝습니다. (3)은 측정에서 7B 모델이 판독에 부족했고 14B는 건당 81초였습니다.
- 정직한 위치: "새로운 우선순위 방법"이 아니라 "LLM을 우선순위 판단에 넣을 때 망가질 수 있는 부분을 코드로 막는 방법"입니다. 발표의 중심을 이쪽으로 옮기는 편이 방어하기 쉽습니다.

### 운영

- 비용(토큰 기준, 가격은 곱해서 계산): SBOM 전용 판단은 기록상 74건에 호출 132회, 입력 29.6만, 출력 9.7만 토큰입니다. 건당 입력 약 4,000, 출력 약 1,300입니다. 레포가 있을 때는 건당 입력 약 8,400, 출력 약 1,300(`docs/onprem-llm.md`)이고, 데모 실행의 로그 누계는 33건에 입력 56.9만, 출력 8.1만으로 건당 입력 약 17,000입니다(오류와 재실행 포함).
- 100개 레포: 후보가 레포당 30건(realworld)에서 150건(NodeGoat, 320건 중 NOW와 NEXT 152건) 사이이므로 3천~1만 5천 건, 입력 2,500만~2억 5천만 토큰 규모입니다. 같은 취약점과 패키지 조합을 레포 간에 재사용하는 캐시가 없습니다. SBOM 전용 판단은 레포와 무관하므로 `(vuln_id, package, version, 서비스 맥락)`으로 캐시하면 크게 줄어듭니다.
- 가장 먼저 깨지는 것: 샌드박스입니다. 패키지 묶음마다 컨테이너를 처음부터 실행하고 단계 상한의 합이 25분입니다(`sandbox.py:23`). PoC에서 동시 4개가 한계였습니다. 그다음이 LLM 속도 제한입니다.
- 속도 제한과 잔액 소진: SDK 재시도 3회 뒤 `LLMError`로 바뀌고 그 항목은 규칙 결과로 대체됩니다(`llm_anthropic.py:53-58`). 실행은 끝까지 가고 `decided_by=agent_fallback`으로 표시됩니다. 좋은 설계입니다. 다만 부하에 따라 같은 입력의 결과가 달라지고, 화면 요약에 대체 건수가 눈에 띄게 나오지 않으면 "AI가 판단했다"고 오해하게 됩니다.
- OSV 장애: 배치 조회가 실패하면 실행 전체가 예외로 멈춥니다(`scan.py:70-71`). 상세 조회 하나가 실패하면 그 항목은 CVSS 5.0, 수정 버전 없음으로 처리되어 NOW가 될 수 없습니다(`scan.py:74`). EPSS API가 죽으면 전 항목이 12.5점을 받아 버킷이 전체적으로 올라갑니다. 외부 장애가 버킷을 조용히 바꿉니다.
- Docker 없음: 검증을 건너뛰고 이벤트에 남깁니다. NOW 항목은 검증 없이 표시됩니다.
- 리플레이: LLM 답은 저장본을 쓰고 계약 검사와 규칙은 현재 코드로 다시 적용합니다. 규칙이 바뀌면 같은 저장본에서 다른 결과가 나옵니다(D37에서 이렇게 썼습니다). "오프라인 재생 동일"은 코드가 같을 때만 참입니다. 새 입력은 리플레이 모드에서 캐시가 없어 실행되지 않습니다.
- API(`api.py`)는 읽기 전용이고 SSE는 저장된 이벤트의 재생입니다. 화면에서 분석을 시작하거나 승인하는 경로는 없습니다. 아키텍처 그림의 "분석 요청", "승인"은 아직 설계입니다.

### 본선 당일 위험 (가능성 높은 순)

1. **입력 형식.** 과제 자료가 컨테이너 이미지 SBOM, 그래프 없는 SBOM, purl 없는 SPDX, Gradle이나 pnpm 레포, 다른 스캐너의 결과 파일일 수 있습니다. 8번의 조용한 누락과 평탄화가 그대로 나옵니다.
2. **OpenAI 어댑터.** 실호출을 한 번도 하지 않았습니다(`llm_openai.py:4`). Responses API와 엄격한 JSON 스키마를 전제로 하는데, 현장 제공 방식이 호환 프록시나 Chat Completions 전용이면 바로 실패합니다. Codex만 제공되고 API 한도가 작으면 후보 수십 건 판단도 어렵습니다.
3. **네트워크와 Docker.** 새 입력은 OSV 실시간 조회가 필요합니다. 현장 네트워크가 막히면 캐시에 있는 기존 실행만 보여줄 수 있습니다. Docker 이미지 반입 여부도 같습니다.
4. **정답이 주어지는 경우.** 주최 측이 기대 결과를 가지고 있으면 현재 일치율 60%대와 과대평가 성향이 그대로 드러납니다.
5. **시연 데이터.** 10번의 낡은 실행을 실수로 열 위험, 규칙 NOW 0건인 데모 레포에서 "규칙이 사실, AI가 판단" 설명이 꼬일 위험이 있습니다.
