## 2. 운영에서 위험한 것

### 2-1. 변경 판정이 버킷 안의 움직임을 놓치고, 그때는 AI 판단이 낡은 채로 남습니다

- 위치: `services.py:110-137`(`diff`), `services.py:190-191`(변화 없음이면 실행을 만들지 않음), `services.py:148-162`(`_carry`).
- 문제 1: 비교가 규칙 버킷끼리만 이루어집니다. EPSS 백분위가 0.50에서 0.97로 올라도 규칙 점수가 33.5에서 54.75로 움직일 뿐 둘 다 NEXT이면 변화가 아닙니다. 그 항목을 AI가 이전에 MONITOR로 내렸다면 현재 실행의 최종 버킷은 MONITOR로 남습니다. D44에서 넣은 "EPSS 0.9 이상은 MONITOR로 내리지 못한다"는 새 판단 때만 적용되고 재확인에서는 다시 평가되지 않습니다. 재현: 위 조건에서 `services.diff(...)`가 빈 목록을 돌려줍니다.
- 문제 2: AI 판단을 옮기는 기준이 Finding id(취약점, 패키지, 버전)뿐입니다. 그 판단의 근거였던 것이 바뀌어도 옮깁니다. 예: "운영 코드에서 쓰지 않으므로 한 단계 낮춤"이라는 판단 뒤에 코드가 그 패키지를 쓰기 시작했는데 규칙 버킷이 그대로인 경우, 서비스 맥락이 바뀐 경우. 옮겨 온 판단은 항목 단위로는 표시되지 않고(`Triage`에 표시 필드 없음, 건수만 `ServiceCheck.carried`) `decided_by`는 `agent`입니다. 판단의 나이에도 제한이 없습니다.
- 문제 3: 기준 실행으로 아무 실행이나 지정할 수 있습니다(`services.py:90`은 실행이 있는지만 봄). 재현: 대상 경로가 다른 서비스 두 개에 같은 실행을 기준으로 등록할 수 있습니다. 다른 저장소의 코드를 읽고 내린 판단이 id가 같다는 이유로 새 실행에 옮겨집니다.
- 추측(환경에 따라 다름): `_carry`와 `rescore`는 리플레이 어댑터를 쓰는데 `agent/llm.py:58`은 `LLM_REPLAY_FROM` 환경 변수가 있으면 새 실행 디렉터리보다 그것을 먼저 봅니다. 시연용으로 이 변수를 설정해 둔 상태에서는 다른 실행의 답을 읽게 됩니다.
- 심각도: 운영 위험.
- 권하는 수정: 변화 판정에 "하향 보류 조건이 새로 걸린 항목"(EPSS 0.9 통과, 운영 코드 import가 새로 생김)을 추가합니다. 옮긴 판단은 `import_sites`와 서비스 맥락이 기준 실행과 같을 때만 재사용하고, 항목에 "이전 판단을 가져옴(날짜)"을 표시합니다. 기준 실행을 지정할 때 그 실행의 `meta.target`이 서비스 대상과 같은지 확인합니다.

### 2-2. 재확인의 실패와 경합

- 실패한 확인도 `last_check.at`을 지금으로 기록하므로(`services.py:213-216`) 다음 시도는 주기(기본 24시간) 뒤입니다. OSV가 잠깐 죽었던 서비스는 하루 동안 다시 확인되지 않습니다.
- 추측(실행하지 않음, 코드 기준): 대상이 스캐너 결과 파일인 서비스는 OSV에 닿지 못해도 스캔이 성공으로 끝납니다(`scan.py:73-77`). 이때 OSV만 알던 항목은 전부 `removed`로 판정되어 새 실행이 만들어지고 현재 실행이 됩니다. `removed`는 알림 대상이 아니라서 조용히 일어납니다. 저장소 대상은 이 경우 실패로 끝나 현재 실행을 유지합니다(테스트 있음).
- `triage services check`는 큐를 거치지 않고 그 자리에서 실행합니다(`__main__.py:84`). 작업자의 같은 서비스 확인과 겹치면 실행이 두 개 생기고 나중에 끝난 쪽이 현재 실행이 됩니다. "서비스당 하나만 돈다"는 큐를 거친 요청에만 성립합니다.
- 작업자가 새 실행을 만든 뒤 서비스 기록을 갱신하기 전에 죽으면 재시도가 실행을 하나 더 만들고 앞의 것은 주인 없는 실행으로 목록에 남습니다.
- 주기 확인 자체의 중복은 찾지 못했습니다. 여러 작업자가 동시에 넣어도 저장 계층이 한 건으로 합칩니다(`store/postgres.py:149-165`, `store/files.py:95-102`).
- 심각도: 운영 위험(첫 두 항목), 사소(나머지).
- 권하는 수정: 실패한 확인은 짧은 간격(예: 15분)으로 다시 시도합니다. `coverage.osv`가 False인 스캔은 비교하지 않고 실패로 처리합니다. 명령줄 확인도 작업을 넣고 `worker --once`와 같은 경로로 실행합니다.

### 2-3. 저장 계층을 거치지 않는 상태

- `agent_answers.json`은 디스크에서 직접 읽고 씁니다(`services.py:150-157`, `runner.py:185`). D45는 큰 산출물을 `out/<run_id>/`에 둔다고 했지만 이 파일은 산출물이 아니라 재확인과 `rescore`가 의존하는 상태입니다. PostgreSQL 모드에서 작업자가 다른 호스트에 있고 `out/`을 공유하지 않으면 `_carry`는 파일이 없다고 보고 0건을 돌려주며 오류도 내지 않습니다(`services.py:151`). 절대 규칙 10의 "두 저장 모드가 같은 동작"이 이 경로에서는 공유 볼륨이라는 전제에 달려 있습니다. `tests/test_store.py`는 이 차이를 잡지 못합니다.
- 서비스 대상 경로도 같습니다. 대상은 "작업자가 보는 경로"인데 등록 검사는 API 프로세스에서 합니다(`HARNESS.md` 한계 칸에 적혀 있음).
- 심각도: 운영 위험. 파일 모드 시연에는 영향이 없습니다.
- 권하는 수정: 기록된 답을 저장 계층의 문서로 옮기거나, PostgreSQL 모드에서 파일이 없으면 0건이 아니라 "가져오지 못함"을 `ServiceCheck`에 남깁니다.

### 2-4. 인증과 요청 출처 검사

깨뜨리려 했으나 찾지 못한 것부터 적습니다. ID 토큰 검증(`auth.py:213-236`)은 비대칭 알고리즘만 받고, 키는 인증 서버의 목록에서 고르며, 발급자, 대상, 만료, nonce, 여러 대상일 때의 `azp`를 확인합니다. 로그인 흐름은 서명한 쿠키에 state, nonce, PKCE 검증값을 묶습니다. `next`는 사이트 안 경로만 받습니다. 쓰기 요청은 Origin 또는 `Sec-Fetch-Site`로 걸러지고 쿠키는 `SameSite=Lax`입니다. `/api/health`와 `/api/me`를 뺀 모든 `/api` 경로에 역할 의존성이 달려 있습니다(`api.py` 전체를 대조). `run_id`에 `..`을 넣어도 404입니다. 서비스 경로 제한은 심볼릭 링크를 푼 뒤 검사합니다.

남는 것

- **TLS를 프록시에서 끝내면 모든 쓰기가 403입니다.** `auth.py:327-340`은 `TRIAGE_PUBLIC_URL`이 없으면 요청의 스킴과 Host로 자기 주소를 만듭니다. 프록시 뒤에서는 스킴이 `http`로 보이는데 브라우저의 Origin은 `https`입니다. 로그인이 꺼져 있어도 같습니다. 재현: 로그인 off, `TRIAGE_PUBLIC_URL` 미설정, Host `triage.example`, Origin `https://triage.example`인 POST가 403. `doctor`의 경고는 oidc 모드에서만 나옵니다(`auth.py:451-452`). 심각도: 운영 위험. 시연을 프록시나 터널 뒤에서 하면 시연 영향입니다. 수정: off 모드에서도 `doctor`가 알리고, `X-Forwarded-Proto`를 신뢰할지 설정으로 둡니다.
- **로그인 off는 모두가 관리 역할입니다**(`auth.py:79`). 시연장 네트워크에서 `0.0.0.0`으로 띄우면 같은 망의 누구나 결정 기록, 샌드박스 작업 시작, 서비스 등록을 할 수 있습니다. 경로는 `TRIAGE_SERVICE_ROOTS`(기본 `fixtures/`)로 제한됩니다. 심각도: 시연 영향은 낮고 운영 위험. 수정: off 모드에서는 `127.0.0.1`이 아닌 주소로 띄울 때 경고합니다.
- 추측: off 모드이고 `TRIAGE_PUBLIC_URL`이 없으면 Origin과 Host가 같기만 하면 통과하므로 DNS 리바인딩으로 로컬 API에 쓰기를 보낼 수 있습니다. 확인하지 않았습니다. 사소.
- 서비스 대상은 등록할 때만 검사합니다. 확인할 때는 저장된 경로를 그대로 씁니다(`services.py:185-188`). 등록 뒤에 허용 위치 설정을 좁히거나 그 경로를 바깥을 가리키는 링크로 바꾸면 검사를 지나칩니다. 허용 위치에 쓸 수 있는 사람만 가능하므로 사소.
- 열람 역할의 조회가 쓰기를 일으킵니다. 작업 조회가 멈춘 작업을 대기열로 되돌립니다(`jobs.py:93-95`). 동작상 해는 없으나 "읽기는 열람"이라는 설명과 다릅니다. 사소.
- `GET /api/runs/{id}/jobs/latest`의 `kind`는 검사하지 않습니다. 재현에서 `../../x`도 200입니다. 경로로 쓰이지 않아 해는 없습니다. 사소.
- 이미 적혀 있는 한계(세션을 서버에서 끊지 못함, 실제 인증 서버 미확인, 서비스별 접근 제한 없음)는 반복하지 않습니다.

### 2-5. 큐

- 구조적 결함은 찾지 못했습니다. 가져가기(`FOR UPDATE SKIP LOCKED`, 파일은 `flock`), 실행 중 작업의 중복 금지(부분 고유 인덱스), 작업을 쥔 작업자만 갱신, 한 번 재시도 뒤 `interrupted`가 코드와 테스트에 있습니다.
- 파일 모드의 가져가기와 목록은 매번 `out/*/jobs/*.json`을 전부 읽습니다(`store/files.py:112-130`). 작업자가 1초마다 돌므로 실행이 수백 개가 되면 느려집니다. 시연 규모에서는 문제없습니다. 사소.
- 파일 모드 기본값에서는 API 프로세스 안의 스레드가 샌드박스를 돌립니다(`jobs.py:65-66`). 절대 규칙 10의 "API 프로세스는 기록만 하고 실행은 작업자가 한다"는 PostgreSQL 모드에서만 문자 그대로 참입니다. 문서에 적혀 있는 선택이지만 규칙 문장과는 어긋납니다. 사소.

## 5. 본선 전 권고 (작은 순)

1. 서비스 시연은 리플레이 모드로 하고, 기준 실행을 지정해 등록할 때 첫 확인을 한 주기 뒤로 미룹니다(1-1).
2. VEX의 영향 없음 상태와 Snyk 라이선스 항목을 제외하고, 표의 알아보지 못한 취약점 id 건수를 안내에 적습니다(1-5).
