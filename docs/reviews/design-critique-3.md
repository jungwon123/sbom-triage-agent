# 설계 비판 3: 쿠버네티스 배포 (D51)

작성일 2026-11-23. 대상은 커밋 `a7e4441`(이미지와 쿠버네티스 매니페스트)과 `bb67353`(샌드박스 복사 수정)입니다.

## 0. 확인한 방법과 범위

- 읽은 것: `Dockerfile`, `.dockerignore`, `deploy/k8s/` 전체, `deploy/k8s/README.md`, HANDOFF D50과 D51, HARNESS의 D51 행 3개, `jobs.py`, `services.py`, `store/postgres.py`, `store/schema.sql`, `verify/sandbox.py`, `verify/run.py`, `decide.py`, `auth.py`의 쓰기 검사, `api.py`.
- 돌린 것: `kubectl kustomize`로 `overlays/local`과 `overlays/multinode` 렌더링(각 13개 리소스), `uv run pytest -q`(전부 통과), 로컬 시험 DB(127.0.0.1:54329)의 임시 스키마에서 재현 스크립트 3개. 임시 스키마는 끝난 뒤 지웠습니다.
- 하지 않은 것: 클러스터와 컨테이너 기동, 이미지 빌드, 모델 호출, `.env` 읽기. 그래서 파드 수명 주기에 관한 지적은 매니페스트와 코드를 읽고 추론한 것이며 항목마다 표시했습니다.
- 요청에서 제외한 항목(실제 NFS, 관리형 DB 제품, 공인 인증서, Calico와 Cilium, 로그인을 켠 인그레스, 노드 장애 시 이어받기, API 8000 개방, http 허용, egress 개방, 특권 사이드카의 위험 자체)은 다시 적지 않았습니다.

심각도 표기: **시연 영향**은 클러스터에서 시연할 때 눈에 보이는 것, **운영 위험**은 운영에서 잘못된 결과나 장애로 이어지는 것, **사소**는 알고 있으면 되는 것입니다. 본선 시연이 리플레이 파일 모드라면 이 보고서의 항목은 시연을 깨뜨리지 않습니다.

## 2. 지적

### 2-1. 클러스터에서는 화면만으로 검증에 닿을 수 없습니다 (시연 영향)

**위치**: `backend/triage/jobs.py:57-58`, `backend/triage/decide.py:151-152`, `backend/triage/decide.py:173-174`, `backend/triage/runner.py:290`, `deploy/k8s/base/worker.yaml:1-4`

**무엇이 문제인가**: 작업 종류는 `export_together`와 `service_check` 두 개뿐입니다. 샌드박스 검증(`runner.verify`)과 AI 판단을 시작하는 작업 종류도 API 경로도 없습니다. 그런데 함께 검증은 `out/<run>/verify/baseline.json`이 있어야 돌고(`decide.py:151`), 내보낼 대상은 검증 결과에 패치 파일이 있는 승인 건만입니다(`decide.py:173-174`). 클러스터에서 재확인이 만든 새 실행에는 둘 다 없습니다.

결과적으로 사이드카를 붙여도 화면에서 할 수 있는 일은 다음과 같습니다.

- 재확인이 만든 실행에서 "함께 검증하고 내보내기"를 누르면 승인 가능한 건이 없어 빈 결과가 나옵니다.
- 검증을 만들려면 `kubectl exec`로 작업자 파드에 들어가 `python -m triage verify`를 손으로 돌려야 합니다. README의 "작업자 파드 안에서 기준선과 3개 패키지 검증이 모두 verified"가 이 방식으로 보입니다.
- `kubectl exec`로 시작한 검증은 큐 밖이라 생존 기록, 이어받기, 종료 유예의 보호를 받지 않습니다.

**근거**: `jobs.HANDLERS`의 키 2개, `api.py`의 경로 목록에 verify와 agent가 없음, `runner.verify`를 부르는 곳은 CLI뿐입니다.

**문서와의 차이**: README 4번은 "기본 구성에서는 검증을 건너뛰고 그 사실이 이벤트에 남습니다"라고 하지만, 건너뜀 이벤트는 `runner.verify`가 불렸을 때만 남습니다(`runner.py:296-299`). 클러스터의 작업자는 그 함수를 부르지 않으므로 아무것도 남지 않습니다. 같은 문단의 "분류, AI 판단, 서비스 다시 확인은 그대로 됩니다"에서 AI 판단도 같은 이유로 `kubectl exec`가 있어야 합니다.

**권고**: 본선 전에는 문서만 고칩니다. "클러스터에서 검증과 AI 판단은 작업자 파드에서 명령으로 돌린다"고 적고 절차를 한 줄 넣습니다. 그 뒤에 `verify` 작업 종류를 추가해 큐로 돌리는 것이 맞습니다.

### 2-2. 종료 신호가 사이드카에도 동시에 가서 진행 중인 검증이 거짓 실패로 기록됩니다 (운영 위험, 추론)

**위치**: `deploy/k8s/base/worker.yaml:19-21`, `deploy/k8s/components/sandbox-dind/worker-dind.yaml:12-22`, `backend/triage/verify/run.py:29-32`, `backend/triage/verify/run.py:40-46`, `backend/triage/verify/sandbox.py:27-33`, `backend/triage/decide.py:154`

**무엇이 문제인가**: `dind`는 일반 컨테이너로 붙어 있습니다. 파드가 종료될 때 kubelet은 모든 컨테이너에 동시에 SIGTERM을 보냅니다. 작업자는 하던 작업을 끝내려고 기다리지만 `dockerd`는 신호를 받으면 돌던 컨테이너를 정리하고 내려갑니다. 그러면 진행 중이던 `docker run`이 0이 아닌 코드로 끝나고, 시간 초과가 아니므로 판정 함수가 그대로 실패로 읽습니다.

- copy, apply, install, setup 단계였다면 `failed`, 사유 `<단계>_failed` (`run.py:29-32`)
- build나 test 단계였다면 기준선은 통과였으므로 `failed`, 사유 `regression` (`run.py:40-46`)

작업은 정상 종료(`done`)로 기록되고 결과에는 "회귀"가 남습니다. 롤링 배포나 노드 비우기 한 번이 조치안에 대한 틀린 판정을 만듭니다. 유예 15분은 사이드카가 살아 있어야 의미가 있는데 지금 구성에서는 그렇지 않습니다.

**시작할 때도 같은 종류의 문제가 있습니다.** 두 컨테이너는 함께 시작합니다. 작업자는 1초 간격으로 큐를 보는데 데몬이 준비되기 전에 작업을 잡으면 `sandbox.available()`이 거짓이 되어 "Docker를 사용할 수 없습니다"로 건너뜁니다(`decide.py:154`). 사이드카가 메모리 한도로 죽었다 살아나는 동안에도 같습니다.

**근거**: 실행하지 않았습니다. 쿠버네티스의 종료 순서와 판정 함수의 분기를 읽고 추론했습니다. 판정 분기는 코드로 확인했습니다.

**권고**:

1. `dind`를 네이티브 사이드카로 옮깁니다(`initContainers`에 넣고 `restartPolicy: Always`, 쿠버네티스 1.29 이상). 주 컨테이너가 끝난 뒤에 종료되고, 시작도 사이드카가 준비된 다음에 주 컨테이너가 뜹니다. `startupProbe`로 `docker info`를 걸어 둡니다.
2. 그 전까지는 `dind`에 `preStop`으로 충분히 긴 대기를 넣어 작업자보다 늦게 내려가게 합니다.
3. 코드에서는 `docker` 클라이언트가 데몬에 닿지 못해 실패한 경우(종료 코드 125, "Cannot connect to the Docker daemon")를 단계 실패가 아니라 `inconclusive`로 분류합니다. 조치안의 잘못과 기반 시설의 잘못을 섞지 않는 것이 이 서비스의 판정 원칙과 맞습니다.

### 2-3. 긴 작업 중 DB 연결이 끊기면 결과를 버리고 다시 돌립니다 (운영 위험, 재현)

**위치**: `backend/triage/jobs.py:147-155`, `backend/triage/jobs.py:167`, `backend/triage/jobs.py:188-189`, `backend/triage/store/postgres.py:25-35`

**무엇이 문제인가**: 두 가지가 겹칩니다.

(가) 작업자의 주 연결은 처리기가 도는 동안 쓰이지 않습니다. 샌드박스 한 번은 몇 분에서 길게는 수십 분입니다. 그 사이 연결이 끊기면(방화벽이나 프록시의 유휴 시간 제한, DB 장애 조치) 처리기는 끝났는데 결과를 쓰는 `job_update`가 예외로 끝납니다(`jobs.py:167`). 이 호출은 `try` 밖에 있고 재시도가 없습니다. 작업은 `running`으로 남았다가 30초 뒤 회수되어 처음부터 다시 돕니다. 두 번째도 같으면 `interrupted`가 됩니다.

재현: 처리기 안에서 주 연결을 `pg_terminate_backend`로 끊었습니다.

```
B first pass raised: AdminShutdown terminating connection due to administrator command
B job after pass 1: running attempts 1
B final: interrupted attempts 2 handler ran 2 times
```

처리기는 두 번 다 끝까지 돌았고 패치 파일도 볼륨에 썼지만, 화면에는 "작업자가 작업 도중 중단되어 끝내지 못했습니다"가 나옵니다.

(나) 생존 기록 스레드는 예외가 한 번 나면 끝납니다. `try`가 `while` 전체를 감싸고 있기 때문입니다(`jobs.py:148-153`). 주석은 "다음 기록이 복구한다"고 하지만 다음 기록은 없습니다.

재현: 0.5초 간격, 4초짜리 작업에서 두 번째 기록에 예외를 넣었습니다.

```
C heartbeats attempted during a 4s job at 0.5s interval: 2 -> job done
```

실제 간격(5초)과 회수 기준(30초)에서는 DB가 잠깐 끊긴 뒤 30초가 지나면 다른 작업자가 같은 작업을 잡아 동시에 돌립니다. 먼저 잡은 쪽의 결과는 버려집니다. 작업자 복제를 늘렸을 때의 중복 실행은 큐의 선점 쿼리가 아니라 이 경로에서 생깁니다.

**유휴 연결이 실제로 끊기는지**는 확인하지 못했습니다(추론). 클라우드의 부하 분산기와 NAT는 보통 4분에서 6분의 유휴 제한을 둡니다. 클러스터 밖 DB 구성이 여기에 해당합니다.

**권고**:

1. 생존 기록의 `try`를 `while` 안으로 옮겨 한 번 실패해도 계속 돌게 합니다.
2. 마지막 `job_update`를 새 연결로 몇 번 재시도합니다. `_conn()`은 닫힌 연결을 다시 열므로 재시도만 넣으면 됩니다.
3. `DATABASE_URL`에 `keepalives=1&keepalives_idle=30`을 권장 값으로 문서에 적습니다.

### 2-4. 샌드박스의 네트워크 단계가 작업자 파드의 신원으로 클러스터 안에 닿습니다 (운영 위험, 추론)

**위치**: `backend/triage/verify/sandbox.py:99-106`, `backend/triage/auth.py:331-346`, `deploy/k8s/base/config.yaml:12`, `deploy/k8s/components/postgres/postgres.yaml:58`, `deploy/k8s/base/policy.yaml:2-3`

**무엇이 문제인가**: apply, install, setup 단계는 `bridge` 네트워크로 돕니다. 사이드카 안의 컨테이너가 내보내는 통신은 파드 주소로 바뀌어 나가므로 클러스터에서 보면 작업자 파드가 보낸 것입니다. 그래서 이 단계의 코드는 다음에 닿습니다.

- `triage-api`의 8000번. 기본 설정은 로그인 꺼짐이고 이때 모든 요청이 관리 역할입니다. 쓰기 검사는 `Origin` 헤더가 없으면 통과합니다(`auth.py:331-340`). 즉 서비스 등록과 해제, 결정 기록을 요청할 수 있습니다.
- DB의 5432번. 작업자 파드에 `triage/db-client` 라벨이 있어 정책이 허용합니다. 비밀번호는 전달되지 않으므로 접속 자체는 인증에서 막힙니다.
- 클라우드라면 노드의 메타데이터 주소(169.254.169.254)와 쿠버네티스 API 주소.

install은 `--ignore-scripts`라 패키지 코드가 실행되지 않습니다. 실제로 코드가 도는 것은 setup 단계입니다(`npx prisma generate` 같은 명령이 분석 대상 저장소의 코드와 내려받은 패키지를 실행). setup 명령은 CLI로만 지정하고 실행 기록에 남아 함께 검증에서 다시 쓰입니다.

노트북의 Docker에서는 같은 단계가 닿을 내부 서비스가 없었습니다. 클러스터로 옮기면서 생긴 차이입니다. "API와 작업자의 egress 개방"은 이미 한계로 적혀 있지만, 신뢰하지 않는 저장소의 코드가 그 열린 길을 같이 쓴다는 점은 적혀 있지 않습니다.

**근거**: 실행하지 않았습니다. Docker의 기본 NAT 동작과 정책의 라벨 선택자를 읽고 추론했습니다. 쓰기 검사가 `Origin` 없는 요청을 통과시키는 것은 코드로 확인했습니다.

**권고**: 작업자 파드에 egress 정책을 둡니다. DNS, DB, 공개 레지스트리와 취약점 피드만 허용하고 클러스터 내부 대역과 169.254.0.0/16을 막습니다. 가능하면 샌드박스가 쓰는 Docker 네트워크를 따로 만들어 사설 대역으로 나가는 통신을 사이드카의 iptables에서 막습니다. 인그레스를 쓰는 구성에서는 로그인을 켠 상태를 기본으로 둡니다.

### 2-5. 이미지에 Syft가 없어 Syft로 만든 기준 실행과 재확인이 어긋납니다 (운영 위험)

**위치**: `Dockerfile`(Syft 설치 없음), `backend/triage/services.py:191-193`, `backend/triage/sbom.py:206-208`, `backend/triage/sbom.py:227-231`

**무엇이 문제인가**: D50은 재확인이 기준 실행과 같은 방식으로 SBOM을 만들게 고쳤습니다. 기준이 Syft면 `use_syft=True`로 부릅니다. 그런데 이미지에는 Syft가 없어 `run_syft`가 `None`을 돌려주고 안내 없이 lock 파일 방식으로 넘어갑니다. 노트북에서 Syft로 만든 실행을 `triage db import`로 옮겨 기준으로 지정하면, 지난 보고서 1-1의 현상(코드가 같은데 몇 건이 달라져 새 실행이 현재 실행이 됨)이 클러스터에서 다시 나옵니다.

### 2-6. `db init`이 동시에 돌면 실패하고, 스키마를 바꾸는 수단이 없습니다 (운영 위험, 재현)

**위치**: `backend/triage/store/postgres.py:38-42`, `backend/triage/store/schema.sql:4-113`, `deploy/k8s/base/api.yaml:22-27`, `deploy/k8s/base/worker.yaml`(초기화 컨테이너 없음)

**동시 실행**: 빈 스키마에서 4개 연결이 동시에 `init()`을 부르는 것을 8번 반복했습니다.

```
A concurrent init: {'ok': 8, 'UniqueViolation: duplicate key value violates unique constraint "pg_type_typname_nsp_index"': 24}
```

매번 하나만 성공하고 나머지는 실패합니다. `CREATE TABLE IF NOT EXISTS`는 동시 실행에 안전하지 않습니다. 복제 2개로 처음 올리면 초기화 컨테이너 하나가 한 번 실패한 뒤 재시작으로 넘어갑니다. 스스로 회복되므로 장애는 아니지만 "여러 번 실행해도 안전"은 "동시에 실행해도 안전"이 아닙니다.

**스키마 변경**: `schema.sql`은 전부 `IF NOT EXISTS`이고 `schema_version`에 1, 2, 3을 무조건 넣습니다. 이미 있는 테이블에 열을 추가하거나 바꾸는 방법이 없고, 버전 3이라고 적혀 있어도 실제 테이블 모양은 처음 만들어진 때의 것입니다. 코드가 기대하는 버전과 DB의 버전을 비교하는 곳도 없습니다.

**롤링 배포**: 작업자에는 초기화 컨테이너가 없고 API와 작업자의 배포 순서가 묶여 있지 않습니다. 스키마가 바뀌는 판에서는 새 작업자가 옛 스키마에서, 옛 API가 새 스키마에서 한동안 돕니다. 작업자는 예외를 잡고 1초마다 다시 시도하므로 죽지는 않습니다.

**권한**: 초기화를 API 파드가 하므로 API가 평소에 쓰는 DB 계정이 테이블 생성 권한을 가집니다.

**권고**: `init()` 첫 줄에 `pg_advisory_xact_lock`을 넣습니다(한 줄). 스키마를 처음 바꿔야 할 때 버전별 마이그레이션(버전마다 SQL을 두고 순서대로 적용)으로 바꾸고, 초기화는 배포 전에 한 번 도는 Job으로 빼서 별도 계정을 씁니다. 그때까지는 문서에 "스키마를 바꾸는 배포는 아직 지원하지 않는다"고 적습니다.

### 2-7. DB 연결에 풀, 시간 제한, 상한이 없습니다 (운영 위험, 추론)

**위치**: `backend/triage/store/postgres.py:23-35`, `deploy/k8s/base/api.yaml:33-43`

**무엇이 문제인가**: 연결은 스레드마다 하나이고 닫지 않습니다. API의 처리 함수는 동기 함수라 스레드 풀(기본 40개)에서 돌고, 스레드마다 연결이 하나씩 생깁니다. API 파드 하나가 최대 40개, 복제 2개면 80개입니다. PostgreSQL 기본 상한은 100이고 관리형 DB의 작은 등급은 그보다 낮습니다. 복제를 늘리면 먼저 닿는 한계가 여기입니다.

`psycopg.connect`에 `connect_timeout`이 없습니다. DB가 응답 없이 사라지면(정책으로 막히거나 주소가 바뀐 경우) 연결 시도가 TCP 시간 제한까지 매달립니다. 준비 점검은 1초 뒤 실패로 처리되지만 그 요청을 맡은 스레드는 계속 묶여 있습니다. 시작 점검은 3초마다 오므로 2분 동안 약 40개가 쌓여 스레드 풀이 찹니다.

DB 장애 조치 뒤에는 스레드마다 죽은 연결을 한 번씩 써 봐야 다시 엽니다. 그동안 요청이 드문드문 500으로 실패합니다.

**근거**: 코드 확인과 추론. 부하를 걸어 연결 수를 세지는 않았습니다.

**권고**: `psycopg_pool`로 파드당 상한이 있는 풀을 씁니다. `DATABASE_URL`에 `connect_timeout=5`를 붙이도록 `secrets.example.env`와 README에 적습니다. 프로브에 `timeoutSeconds`를 명시합니다.

### 2-8. 내보내기 폴더를 API와 작업자가 잠금 없이 함께 지우고 씁니다 (운영 위험, 추론)

### 2-10. PDB와 복제 수가 맞지 않는 구성이 있고 작업자에는 점검이 없습니다 (사소)

**위치**: `deploy/k8s/base/policy.yaml:23-31`, `deploy/k8s/overlays/local/kustomization.yaml:24-28`, `deploy/k8s/base/worker.yaml`

- `overlays/local`의 렌더링 결과는 API 복제 1개에 `minAvailable: 1`입니다. 이 조합에서는 노드 비우기가 끝나지 않습니다. 노드 하나짜리 시험용이라 실해는 작습니다.
- `policy.yaml:23`의 주석 "Losing a node must not take every API pod with it"는 PDB가 하는 일이 아닙니다. PDB는 자발적 퇴거만 막습니다. 노드가 죽는 경우를 막는 것은 배치 분산인데 `whenUnsatisfiable: ScheduleAnyway`라 보장이 아닙니다.
- 준비 점검이 DB를 읽으므로 DB가 끊기면 준비된 API 파드가 0개가 되고, 그동안 PDB가 노드 비우기를 모두 막습니다(추론).
- 작업자에는 프로브가 없습니다. 생존 기록은 별도 스레드가 쓰므로 처리기가 멈춰도(`sandbox.py:96`과 `sandbox.py:115`의 `docker volume` 호출에는 시간 제한이 없음) 기록은 계속 갱신되고 작업은 회수되지 않습니다. 생존 기록이 "살아 있음"이 아니라 "스레드가 돌고 있음"을 뜻합니다.

**권고**: local에서는 PDB를 빼거나 `maxUnavailable: 1`로 둡니다. 주석을 고칩니다. 작업 한 건의 최대 시간을 정해 넘으면 회수합니다.

### 2-11. 이미지에 들어간 것과 빠진 것 (사소)

**위치**: `Dockerfile:31`, `Dockerfile:36`, `.dockerignore:3-5`, `backend/triage/verify/sandbox.py:19`, `deploy/k8s/components/sandbox-dind/worker-dind.yaml:13`

### 2-12. 자원 한도와 작업 시간 (사소)

**위치**: `backend/triage/verify/sandbox.py:20-23`, `backend/triage/verify/run.py:139`, `deploy/k8s/components/sandbox-dind/worker-dind.yaml:23-30`, `deploy/k8s/base/worker.yaml:21`

- 메모리: 샌드박스 컨테이너는 `--memory 2g`이고 사이드카 한도는 4Gi입니다. 샌드박스는 한 번에 하나만 돌므로 한도 안에 들어갑니다. 문제를 찾지 못했습니다.
- 디스크: `/var/lib/docker`가 크기 제한 없는 `emptyDir`입니다. 이미지, 샌드박스 볼륨(`node_modules` 포함), 중단된 작업이 남긴 볼륨이 노드의 임시 저장소에 쌓입니다. `ephemeral-storage` 요청과 한도가 없어 노드가 디스크 압박을 받으면 작업자 파드가 먼저 퇴거됩니다. `emptyDir.sizeLimit`과 요청 값을 둡니다.
- README 4번의 "사이드카를 새로 띄울 때마다 이미지를 다시 받습니다"는 조금 다릅니다. `emptyDir`은 파드가 사는 동안 유지되므로 사이드카 컨테이너만 재시작하면 캐시는 남고, 파드가 새로 뜰 때만 다시 받습니다. 대신 사이드카가 죽으며 남긴 컨테이너와 볼륨도 같이 남습니다.
- 시간: 단계별 제한의 합은 1,500초이고 함께 검증은 명령 수에 따라 최대 4배(6,000초)입니다. 종료 유예 900초는 보통의 경우를 덮지만 최악의 경우는 덮지 못합니다. 유예를 넘으면 강제 종료와 한 번의 재실행으로 이어집니다. README의 "하던 작업을 끝내고 내려갑니다"에 "15분 안에 끝나는 작업은"이라는 조건이 붙어야 합니다.
- CPU: `--cpus 2`인데 사이드카의 CPU 요청은 500m이고 한도는 없습니다. 노드가 바쁘면 단계 시간이 늘어 시간 초과(`inconclusive`)가 늘어납니다.

## 3. 깨뜨리지 못한 것

- 작업 선점과 중복 방지: `FOR UPDATE SKIP LOCKED`와 부분 고유 인덱스는 작업자 복제를 늘려도 한 작업을 한 작업자만 잡게 합니다. 예약(`submit_due`)을 여러 작업자가 동시에 불러도 같은 서비스의 확인은 하나만 들어갑니다. 중복 실행이 생기는 길은 2-3의 생존 기록 쪽뿐이었습니다.
- 실행 폴더 이름 충돌: 같은 초에 만들어도 서비스 이름이 들어가고 접미사를 붙이므로 서로 다른 작업자가 같은 폴더에 쓰지 않습니다.
- 사이드카와 샌드박스에 시크릿이 들어가지 않습니다.
- API의 롤링 배포: 복제 2개에서 기본 전략은 새 파드가 준비된 뒤 옛 파드를 내립니다. 준비 점검이 실제로 DB를 읽는 것과 생존 점검이 포트만 보는 것은 주석대로입니다.
- 네임스페이스: 두 overlay의 렌더링 결과에서 모든 리소스가 `sbom-triage`에 있습니다.

## 6. 권고 순서

본선(2026-11-24 ~ 25) 전에 코드를 바꾸는 것은 권하지 않습니다. 시연이 리플레이 파일 모드라면 위 항목은 시연에 닿지 않습니다. 본선 전에 할 것은 문서 두 가지입니다.

1. README에 "클러스터에서 검증과 AI 판단은 작업자 파드에서 명령으로 돌린다"를 적습니다 (2-1). 심사에서 "쿠버네티스에서 검증까지 됩니까"라는 질문에 "사이드카로 검증이 돌고, 시작은 아직 명령으로 합니다"라고 답할 수 있어야 합니다.
2. README의 남은 한계에 Syft 부재(2-5), 종료 시 사이드카 문제(2-2), 스키마 변경 미지원(2-6)을 추가합니다.

본선 뒤의 순서는 다음을 권합니다.

1. 생존 기록의 `try` 위치와 결과 기록 재시도 (2-3). 몇 줄이고 재현 스크립트가 그대로 테스트가 됩니다.
2. `init()`의 advisory lock (2-6). 한 줄입니다.
3. 데몬에 닿지 못한 실패를 `inconclusive`로 분류하고, `dind`를 네이티브 사이드카로 (2-2).
4. 작업자 egress 정책 (2-4).
5. `verify` 작업 종류 추가 (2-1).
6. Syft를 이미지에 넣거나 없을 때 실패로 처리 (2-5).
7. 연결 풀과 시간 제한 (2-7), 내보내기 직렬화 (2-8), 시크릿 분리 (2-9).
