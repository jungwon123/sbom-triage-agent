# 키워드 사전

프론트엔드 개발자 기준으로 이 프로젝트를 이해하고 설명하는 데 필요한 개념을 정리했습니다. 2026-11-23의 구현 기준입니다.

표의 세 번째 칸은 그 개념이 이 저장소의 어디에 어떻게 쓰이는지입니다. 괄호 안의 D숫자는 `HANDOFF.md` 2장의 결정 번호, F숫자는 `docs/REQUIREMENTS.md`의 요구 번호입니다. 묶음 끝의 "스스로 확인"은 그 묶음을 이해했는지 점검하는 질문입니다.

기능이 실제로 어떻게 동작해야 하는지는 `docs/GUIDE.md`에, 더 읽을 자료는 `docs/reading-list.md`에 있습니다.

## 읽는 순서

1. **먼저 익힐 12개 (★)**: SBOM, EPSS, reachability, 버킷, 하이브리드 판단과 ±1 제약, NOW 누락, 프롬프트 인젝션, 일회용 컨테이너, 기준선 비교, 검증 강도, 작업 큐와 작업자, NetworkPolicy.
2. 1 ~ 4장은 **제품이 무엇을 판단하는가**입니다. 이 프로젝트의 핵심입니다.
3. 5 ~ 10장은 **그 판단을 어떻게 운영하는가**입니다. 11월 19일 이후에 만든 부분입니다.

## 1. 공급망 보안

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| ★ SBOM / CycloneDX / SPDX | SBOM은 소프트웨어의 부품(패키지) 명세서입니다. CycloneDX와 SPDX는 이를 쓰는 두 가지 표준 형식입니다. `package.json`을 표준 양식으로 풀어 쓴 목록에 가깝습니다. | ①단계가 `sbom.cdx.json`을 만들고 스캔은 이것만 입력으로 씁니다(D20, F2-5). 남이 만든 SBOM 파일도 입력으로 받습니다. |
| Syft | 코드 폴더를 읽어 SBOM을 만드는 오픈소스 도구입니다. | `sbom.py`가 호출하고, 없거나 실패하면 lock 파일을 직접 해석합니다(F2-2). 컨테이너 이미지에는 Syft가 들어 있습니다. |
| OSV | 오픈소스 취약점 공개 DB와 API입니다. | `querybatch`로 ID를 받고 상세는 따로 조회합니다(F3-1). |
| CVE / GHSA | 취약점 번호입니다. CVE는 범용, GHSA는 GitHub 권고문 번호입니다. | npm은 GHSA가 기본이고 CVE가 없을 수 있습니다. EPSS는 CVE에만 있어 없으면 `None`입니다. |
| MAL- (악성 패키지) | 패키지 자체가 공격인 경우의 권고문 번호입니다. 결함이 아니라 악성 코드입니다. | 점수와 무관하게 NOW입니다(`score.floor`, D44). |
| CVSS | 이론상 최악일 때의 심각도(0 ~ 10)입니다. 실제 악용이나 사용 여부는 반영하지 않습니다. | 위험 점수 100점 중 25점의 입력입니다. 화면에서 CVSS 정렬과 버킷 보기를 바꿔 비교할 수 있습니다(F7-4). |
| ★ EPSS | 앞으로 30일 안에 실제 공격에 쓰일 확률을 예측한 점수입니다. FIRST가 제공합니다. | 위험 점수 25점의 입력입니다. 백분위 0.8 아래는 0점으로 칩니다. 분포가 한쪽으로 쏠려 있어서입니다(D38). |
| KEV | 미국 CISA가 실제 악용을 확인한 취약점 목록입니다. | 운영 의존성이면 NOW, 개발 전용이면 최소 NEXT입니다. AI가 내릴 수 없습니다(F6-9). |
| transitive dependency | 설치한 패키지가 끌고 온 간접 의존성입니다. 직접 의존성은 `direct`입니다. | 노출 가중치가 direct 1.0, transitive 0.7입니다. |
| ★ reachability(도달성) | 취약한 패키지를 우리 코드가 실제로 쓰는지 따지는 개념입니다. | `used_symbol`, `imported_only`, `unused`, `unknown` 네 값입니다. 1차는 import 검색(F4-4), 2차는 AI가 코드를 읽어 판정합니다(F6-1). 소스가 없는 입력(SBOM 파일)은 `unknown`이고 노출 가중치를 0.4로 둡니다. |
| purl | 패키지를 가리키는 표준 주소입니다. `pkg:npm/lodash@4.17.20`처럼 생태계, 이름, 버전이 들어 있습니다. | SBOM의 컴포넌트를 OSV에 물을 때 씁니다. 해석하지 못한 것은 `coverage.unsupported`에 남깁니다. |

**스스로 확인:** CVSS가 높으면 먼저 고쳐야 하지 않는가?
**답:** CVSS는 이론상 최악의 크기일 뿐이라, 악용 확률(EPSS)과 실제 사용 여부(reachability)를 함께 봅니다.

## 2. 판단 설계

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| 규칙 점수(risk, effort) | 사람이 정한 수식의 점수입니다. 같은 입력이면 항상 같은 결과가 나옵니다. | `score.py`의 순수 함수입니다. 위험 100점 = 심각도 25 + 악용 가능성 25 + 노출 50(F5-1, D13). effort는 조치 비용입니다. |
| 순수 함수 | 입력만으로 결과가 정해지고 바깥 상태를 건드리지 않는 함수입니다. React의 순수 컴포넌트와 같은 생각입니다. | 점수 계산은 파일도 네트워크도 읽지 않습니다. 그래서 테스트하기 쉽고 재현됩니다. |
| ★ 버킷 | 이번 주, 다음 정기 작업, 지켜보기의 세 칸 분류입니다. | NOW는 60점 이상, NEXT는 30점 이상(또는 60점 이상인데 수정 버전이 없음), MONITOR는 그 아래입니다(F5, D7). |
| 하한(floor) | 점수가 낮아도 사실 때문에 내려갈 수 없는 최저 버킷입니다. | 악성 패키지와 KEV 항목에 적용됩니다(D44). |
| 경보 피로 | 경고가 너무 많아 전부 무시하게 되는 현상입니다. | 이 프로젝트가 푸는 문제입니다. |
| ★ 하이브리드 판단과 ±1 제약 | 숫자는 규칙이, 코드 맥락은 AI가 맡습니다. AI는 버킷을 한 단계만 바꿀 수 있고 이유가 필수입니다. | D5, D6. 어기면 규칙 결과를 씁니다. |
| 하향 안전장치 | AI가 위험한 항목을 낮추는 사고를 코드로 막는 규칙입니다. | KEV와 악성 패키지는 하향 금지입니다. EPSS 백분위 0.9 이상이면서 실행 코드가 import하거나 규칙 버킷이 NOW이면 `needs_review`로 표시하고 사람에게 넘깁니다(F6-9, D37). |
| golden set, 일치율 | 사람이 매긴 정답 모음과, 시스템이 그 정답과 같은 비율입니다. | `triage eval`이 CVSS 정렬, 규칙 단독, 규칙과 AI 세 가지를 비교합니다. |
| 블라인드 세트 | 규칙을 보지 않고 따로 만든 정답 자료입니다. 규칙을 그 자료에 맞춰 고쳤는지 의심받지 않기 위한 것입니다. | `fixtures/blind/`, `fixtures/blind2/`. |
| ★ NOW 누락 | 정답이 NOW인데 최종이 MONITOR인 건수입니다. | 목표 0건입니다. 놓치는 것이 과잉 경고보다 비싸서 일치율과 따로 봅니다. |
| 과대평가, 과소평가 | 정답보다 높게 또는 낮게 분류한 것입니다. | 과소평가가 더 위험합니다. 지금 규칙은 과대평가 쪽으로 기울어 있습니다. |

**스스로 확인:** 정확도는 얼마인가?
**답:** 측정한 표본이 작다는 것을 함께 말해야 합니다. 두 번째 블라인드 세트(45건)에서 규칙 단독 26건, CVSS 정렬 18건이 일치했고 NOW 누락은 0건이었습니다. 데모 실행의 사람 라벨 10건에서는 규칙과 AI가 8건, 규칙 단독 7건, CVSS 정렬 7건이었습니다. 블라인드 세트의 정답은 사람이 아니라 별도 AI 세션이 만든 것입니다.

## 3. AI 에이전트

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| tool use | LLM이 함수 호출을 요청하고 우리 코드가 대신 실행하는 방식입니다. | `get_finding`, `search_usages`, `read_file`, `get_advisory` 등 읽기 전용 도구만 있고 항목당 최대 6회입니다. |
| 스키마 강제 | LLM 출력을 정해진 JSON으로만 받아 Pydantic으로 검사합니다. API 응답을 TypeScript 타입으로 좁히는 것과 비슷합니다. | 출력 타입 `AgentVerdict`에는 점수 필드가 없습니다. 어기면 다시 시도하고, 그래도 안 되면 규칙 결과를 씁니다(`decided_by=agent_fallback`). |
| ★ 프롬프트 인젝션 | 코드나 문서에 숨긴 문장으로 LLM을 조종하는 공격입니다. | 분석 대상 코드와 권고문은 신뢰할 수 없는 입력으로 봅니다. LLM이 쓴 문자열을 실행하지 않고 코드가 명령을 조립합니다(D15, F8-11). |
| 자리표시자 근거 | AI가 `{cvss}`처럼 쓰면 코드가 실제 값을 채웁니다. 템플릿 치환과 같습니다. | D18, F6-3. AI가 숫자를 지어내지 못하게 하는 장치이고, 자리표시자가 아닌 숫자는 테스트가 잡습니다. |
| 어댑터 | 서로 다른 것을 같은 모양으로 쓰게 해 주는 얇은 층입니다. | `agent/llm.py`가 인터페이스이고 anthropic, openai, local, replay 구현이 있습니다. 모델을 바꿔도 나머지 코드는 그대로입니다. |
| 2단계 모드 | 코드를 읽는 모델과 판단문을 쓰는 모델을 나누는 구성입니다. | 사내 모델만 소스코드를 읽고, 외부 모델은 사실(패키지, 점수, 판독 결과)만 받습니다. 외부 모델에는 도구도 주지 않습니다(D35, 규칙 9). |
| 재생(replay) | 저장해 둔 응답으로 같은 실행을 다시 만드는 것입니다. | `DEMO_MODE=replay`에서는 네트워크, Docker, 모델 호출 없이 돕니다. 외부 응답은 `fixtures/cache/`에, AI의 답은 실행 폴더에 남습니다. |
| human-in-the-loop | 최종 실행 전에 사람이 확인하는 단계입니다. | 원본 저장소 반영은 사람이 승인한 뒤 패치와 PR 초안으로만 나갑니다. |

**스스로 확인:** AI를 속여 악성 명령을 실행하게 할 수 있지 않은가?
**답:** AI는 조치의 종류와 버전만 제안합니다. 실행 명령은 코드가 검증된 값으로 조립하고 AI의 도구는 전부 읽기 전용입니다.

## 4. 샌드박스 검증

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| ★ 일회용 컨테이너 | 한 번 쓰고 버리는 격리된 Docker 실행 환경입니다. | 조치안을 실제로 적용해 봅니다. 원본은 건드리지 않고 컨테이너 안의 복사본만 고칩니다(F8-2). |
| `--ignore-scripts` | npm 설치 때 패키지 스크립트의 자동 실행을 막습니다. | 설치 스크립트를 이용한 공격을 차단합니다(F8-7). 그래서 `prisma generate` 같은 생성 단계는 `--setup`으로 따로 줍니다. |
| cap-drop | 컨테이너의 리눅스 권한을 빼는 Docker 옵션입니다. | `--cap-drop ALL`과 메모리 2GB, CPU 2개, 프로세스 512개 제한이 걸려 있습니다. |
| egress 제한 | 안에서 밖으로 나가는 통신을 제한하는 것입니다. 들어오는 쪽은 ingress입니다. | 설치만 네트워크를 쓰고 빌드와 테스트는 `--network none`입니다(F8-7). |
| ★ 기준선 비교 | 조치 전 결과와 조치 후 결과를 비교하는 것입니다. | 조치 전에 이미 실패하던 테스트는 조치의 탓이 아니므로, 새로 깨진 것(회귀)만 실패로 봅니다(D16, D28). |
| overrides | 간접 의존성의 버전을 고정하는 npm 기능입니다. | 간접 의존성을 올리는 조치(`override_transitive`)에 씁니다. |
| lock 파일 | 설치된 정확한 버전과 구조를 기록한 파일입니다. | 운영과 개발 구분, 직접과 간접 구분의 근거입니다. |
| ★ 검증 강도와 verdict | verdict는 `verified`, `failed`, `inconclusive`입니다. 검증 강도는 실제로 실행된 테스트 수입니다. | 테스트가 없는 저장소는 `verified`여도 설치와 재스캔만 확인된 것입니다. 그래서 판정 옆에 테스트 수를 함께 보여 줍니다(D30). |
| `inconclusive` | 통과도 실패도 아닌 "판단할 수 없음"입니다. | 시간 초과, 실행된 테스트 수 감소, Docker 데몬 부재(`sandbox_unavailable`)가 여기에 들어갑니다. 환경 문제를 조치안의 실패로 기록하지 않기 위해서입니다. |

**스스로 확인:** 검증됐다는 것은 안전하다는 뜻인가?
**답:** 아닙니다. 조치를 적용해도 기존에 통과하던 테스트가 계속 통과하고 취약점이 사라졌다는 뜻입니다. 테스트가 적은 저장소에서는 증거가 약하므로 실행된 테스트 수를 함께 봅니다.

## 5. 입력 계층

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| 정규화 | 여러 모양의 입력을 하나의 모양으로 맞추는 것입니다. | `ingest.py`가 무엇이 들어오든 `Component`(패키지 이름, 버전, 생태계) 목록으로 바꿉니다(D49). |
| 스캐너 결과 | Trivy, Grype, OSV-Scanner, Snyk, Dependency-Check 같은 도구가 이미 찾아 둔 취약점 목록입니다. | 입력으로 받습니다. 스캐너가 보고한 취약점은 OSV에 없어도 버리지 않습니다. |
| 형식 판별 | 파일 이름이 아니라 내용을 보고 무슨 형식인지 알아내는 것입니다. | `triage inspect`가 읽기 전용으로 판별하고 읽을 수 없으면 이유를 말합니다. |
| 열 대응 | 표의 어느 열이 이름이고 버전인지 알려 주는 것입니다. | CSV나 처음 보는 JSON 목록은 `--columns name=<열>,version=<열>`로 읽습니다. |
| coverage | 입력 중 얼마나 처리했는지의 기록입니다. | 조회하지 못한 컴포넌트, 빠진 정보(의존 관계, 운영과 개발 구분)를 실행 기록에 남깁니다. 조용히 버리지 않습니다. |

**스스로 확인:** 처음 보는 형식의 자료를 받으면 무엇부터 하는가?
**답:** `triage inspect`로 판별합니다. 표나 목록이면 열을 지정해 읽고, 그래도 안 될 때만 파서를 추가합니다.

## 6. 저장 계층

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| 저장 계층(인터페이스) | 어디에 저장하는지를 나머지 코드가 모르게 하는 층입니다. 프론트에서 API 호출을 한 모듈에 모아 두는 것과 같습니다. | `store/base.py`가 인터페이스이고 `files.py`와 `postgres.py`가 구현입니다. `TRIAGE_STORE`로 고릅니다(D45). |
| 두 모드 동치 | 어느 구현을 쓰든 같은 결과가 나와야 한다는 약속입니다. | `tests/test_store.py`가 같은 테스트를 두 구현에 돌립니다(규칙 10). |
| JSONB | PostgreSQL의 검색 가능한 JSON 열 타입입니다. | Finding, Triage, 이벤트의 본문을 JSONB로 저장합니다. 스키마가 `models.py`에 있어 열로 풀지 않았습니다. |
| 연결 풀 | DB 연결을 미리 만들어 두고 빌려 쓰는 것입니다. 매번 새로 연결하지 않습니다. | `psycopg_pool`을 씁니다. 빌려줄 때 연결이 살아 있는지 검사하고 상한과 시간 제한이 있습니다(D52). |
| keepalive | 연결이 살아 있는지 주기적으로 확인하는 TCP 기능입니다. | DB가 말없이 사라졌을 때 연결이 영원히 멈춰 있지 않게 합니다. |
| advisory lock | 행이 아니라 약속한 번호에 거는 잠금입니다. | 파드 여러 개가 동시에 테이블을 만들려 할 때 차례를 세웁니다. |
| 마이그레이션 | DB 구조의 변경을 버전 번호가 붙은 파일로 관리하는 것입니다. | `store/migrations/<버전>_<이름>.sql`을 순서대로 한 번씩 적용합니다. |
| 원자적 교체 | 중간 상태가 보이지 않게 한 번에 바꾸는 것입니다. | 내보내기는 임시 폴더에 쓰고 `os.replace`로 바꿔 넣습니다. 도중에 실패해도 이전 결과가 남습니다. |
| 단일 장애점 | 하나가 죽으면 전체가 멈추는 구성 요소입니다. | PostgreSQL이 해당합니다. 실제 장애 조치는 시험하지 않았습니다. |

**스스로 확인:** 왜 저장 구현이 두 개인가?
**답:** 파일 구현은 네트워크와 DB 없이 돌아야 하는 오프라인 실행과 테스트를 위한 것이고, PostgreSQL 구현은 여러 프로세스가 같은 기록을 쓰는 운영을 위한 것입니다.

## 7. 작업 큐와 작업자

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| ★ 작업 큐, 작업자 | 큐는 할 일 목록이고 작업자는 그것을 꺼내 실행하는 별도 프로세스입니다. | 몇 분씩 걸리는 일(검증, AI 판단, 함께 검증하는 내보내기, 서비스 다시 확인)은 API가 기록만 하고 작업자가 실행합니다(D46, 규칙 10). |
| 비동기 작업과 폴링 | 요청은 바로 "접수됨"으로 답하고, 결과는 나중에 다시 물어 확인하는 방식입니다. | API가 202를 돌려주고 화면이 3초마다 작업 상태를 묻습니다. |
| `FOR UPDATE SKIP LOCKED` | 다른 작업자가 이미 잡은 행을 기다리지 않고 건너뛰는 SQL입니다. | 작업자 여러 개가 같은 작업을 집지 않으면서 서로 막지도 않습니다. |
| 생존 기록(heartbeat) | "아직 일하고 있다"는 표시를 주기적으로 남기는 것입니다. | 5초마다 갱신합니다. 30초 동안 없으면 그 작업자가 죽은 것으로 봅니다. |
| 되찾기(reclaim) | 죽은 작업자가 잡고 있던 작업을 큐로 돌려놓는 것입니다. | 한 번은 다시 시도하고, 또 끊기면 `interrupted`로 끝냅니다. |
| fencing | 죽은 줄 알았던 옛 작업자가 뒤늦게 결과를 쓰는 것을 거절하는 장치입니다. | 작업을 갱신할 때 그 작업을 잡고 있는 작업자인지 확인합니다. |
| at-least-once, 멱등성 | "최소 한 번 실행"(두 번일 수 있음)과 "여러 번 해도 결과가 같음"입니다. | 작업은 다시 실행될 수 있습니다. 샌드박스는 일회용이라 다시 돌려도 안전하고, AI 판단은 저장된 답을 재사용합니다. |
| 값으로 넘기기 | 작업의 입력을 함수나 객체가 아니라 저장 가능한 값으로만 넘기는 것입니다. | 작업은 DB의 기록이므로 다른 프로세스가 읽어 실행할 수 있어야 합니다. |

**스스로 확인:** 여러 팀이 동시에 요청하면 어떻게 되는가?
**답:** 요청은 큐에 쌓이고 작업자가 하나씩 처리합니다. 작업자 수를 늘리면 병렬로 처리합니다. 작업 하나의 최대 시간과 화면에서의 비용 상한은 아직 없습니다.

## 8. 로그인과 권한

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| OIDC (OpenID Connect) | 회사의 인증 서버로 로그인을 위임하는 표준입니다. "구글로 로그인"과 같은 방식입니다. | `TRIAGE_AUTH=oidc`일 때 씁니다. 기본은 `off`입니다(D47). |
| 인가 코드 흐름 | 브라우저는 일회용 코드만 받고, 서버가 그 코드를 토큰으로 바꾸는 방식입니다. 토큰이 브라우저에 노출되지 않습니다. | `auth.py`가 구현합니다. |
| PKCE | 코드를 가로채도 쓸 수 없게 하는 장치입니다. 시작할 때 만든 비밀값을 끝낼 때 다시 내야 합니다. | 로그인을 시작할 때 verifier를 만들고 S256 방식으로 보냅니다. |
| state, nonce | 로그인 응답이 내가 시작한 그 로그인의 것인지 확인하는 임의의 값입니다. | 둘 다 검사합니다. 맞지 않으면 거절합니다. |
| ID 토큰, JWKS | ID 토큰은 인증 서버가 서명한 "이 사람이 누구인지"의 증명이고, JWKS는 그 서명을 확인할 공개 키 목록입니다. | 서명, 발급자, 만료, nonce를 확인합니다. 서명 없는 방식(`none`)과 대칭 키 방식은 받지 않습니다. |
| 서명된 세션 쿠키 | 서버가 서명한 쿠키입니다. 내용은 보이지만 고치면 서명이 맞지 않게 됩니다. | HMAC-SHA256으로 서명합니다. 서버에 세션 저장소가 없어도 API 파드 여러 개가 같은 쿠키를 인정합니다. |
| 역할 | 무엇을 할 수 있는지의 묶음입니다. | 열람(읽기), 승인(결정, 내보내기, 작업 시작), 관리(서비스 등록과 해제)입니다. 인증 서버의 그룹을 역할로 바꿉니다. |
| 서버 쪽 권한 검사 | 화면에서 버튼을 숨기는 것은 안내일 뿐이고, 막는 것은 서버여야 한다는 원칙입니다. | `/api/health`와 `/api/me`를 뺀 모든 경로에 역할 검사가 있습니다(규칙 11). |
| CSRF | 다른 사이트가 내 브라우저를 시켜 쓰기 요청을 보내게 하는 공격입니다. 쿠키가 자동으로 따라가기 때문에 생깁니다. | 쓰기 요청의 `Origin`이 `TRIAGE_PUBLIC_URL`과 같은지 확인합니다. 이 값이 틀리면 쓰기가 전부 403이 됩니다. |

**스스로 확인:** 화면에서 승인 버튼을 숨기면 충분한가?
**답:** 아닙니다. API를 직접 부르면 그만이므로 서버가 역할을 검사해야 합니다. 로그인이 켜져 있으면 결정한 사람의 이름도 요청 본문이 아니라 세션에서 가져옵니다.

## 9. 서비스 재분류와 알림

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| 서비스 등록 | 한 번 분석하고 끝내지 않고 계속 지켜볼 대상을 등록하는 것입니다. | `triage services add`. 확인 주기를 시간 단위로 정합니다(D48). |
| 기준 실행 | 비교의 기준이 되는 현재 실행입니다. | 다시 스캔한 결과를 이것과 비교합니다. |
| 재분류 | 코드가 그대로여도 세상이 바뀌면 분류가 바뀌는 것입니다. 새 취약점이 공개되거나 KEV에 오르는 경우입니다. | 달라졌을 때만 새 실행을 만듭니다. 모델을 부르지 않습니다. |
| 변경 종류 | 무엇이 어떻게 달라졌는지의 분류입니다. | `added`, `removed`, `raised`, `lowered`, `kev_added`, `fix_released` 여섯 가지입니다. |
| 웹훅 | 정해진 주소로 HTTP 요청을 보내 알리는 방식입니다. | Slack 호환 웹훅으로 요약만 보냅니다. 소스코드는 싣지 않습니다(`notify.py`). |
| 경로 제한 | 화면에서 지정할 수 있는 경로를 정해진 폴더 아래로 묶는 것입니다. | `TRIAGE_SERVICE_ROOTS`. 화면에서 서버의 아무 폴더나 읽게 하지 않기 위해서입니다. |

**스스로 확인:** 다시 확인했더니 새 항목이 생겼다. 그 항목의 버킷은 누가 정한 것인가?
**답:** 규칙입니다. 재확인은 모델을 부르지 않으므로, AI 판단을 다시 받기 전까지는 규칙 결과입니다. 화면의 "달라진 N건만 판단"이 그 항목들만 AI에 보냅니다.

## 10. 컨테이너와 쿠버네티스

쿠버네티스는 기능을 더하지 않습니다. 같은 프로그램을 여러 대에서 죽지 않게 돌리는 운영 수단입니다. 구성과 한계는 `deploy/k8s/README.md`에 있습니다.

| 키워드 | 뜻 | 우리 프로젝트에서 |
|---|---|---|
| 컨테이너 이미지 | 프로그램과 실행에 필요한 것을 한 덩어리로 묶은 것입니다. | 이미지 하나로 API(`uvicorn`)와 작업자(`python -m triage worker`)를 둘 다 띄웁니다(D51). |
| 파드(Pod) | 쿠버네티스가 띄우는 가장 작은 단위입니다. 컨테이너 한 개 또는 함께 사는 여러 개입니다. | API 파드, 작업자 파드가 있습니다. |
| Deployment | "이 파드를 몇 개 유지하라"는 선언입니다. 죽으면 다시 띄우고, 새 버전으로 하나씩 교체합니다. | API는 2개, 작업자는 1개가 기본입니다. |
| Service | 파드들의 앞에 붙는 고정된 이름과 주소입니다. 파드는 죽고 새로 뜨면서 주소가 바뀌기 때문입니다. | `triage-api`. |
| 인그레스(Ingress) | 클러스터 밖에서 들어오는 HTTP 요청을 안의 Service로 보내는 문입니다. TLS(https)도 여기서 끝냅니다. | `components/ingress`. 시험 클러스터에서는 Traefik이 처리했습니다. |
| ConfigMap, Secret | 설정과 비밀값을 이미지 밖에 두는 방법입니다. | 설정은 생성되는 ConfigMap에, 키는 손으로 만드는 Secret에 둡니다. Secret은 커밋하지 않습니다. |
| 컨테이너별 시크릿 | 한 Secret을 통째로 주지 않고 컨테이너마다 필요한 키만 주는 것입니다. | 작업자는 로그인 서명 키를 받지 않고, 샌드박스는 아무 키도 받지 않습니다(D52). |
| PVC, ReadWriteMany | PVC는 "저장 공간을 달라"는 요청입니다. ReadWriteMany는 여러 노드의 파드가 동시에 쓸 수 있는 종류입니다. | `out/`(SBOM, 로그, 패치)은 API와 작업자가 함께 써야 해서 노드가 여럿이면 ReadWriteMany가 필요합니다. |
| 초기화 컨테이너 | 본 컨테이너보다 먼저 실행되고 끝나는 컨테이너입니다. | `db-init`이 테이블을 만듭니다. |
| 사이드카, 네이티브 사이드카 | 본 컨테이너 옆에서 보조 일을 하는 컨테이너입니다. 네이티브 사이드카는 먼저 뜨고 나중에 내려가는 것이 보장됩니다. | 샌드박스를 돌릴 Docker 데몬(dind)을 작업자 옆에 붙입니다. 데몬이 준비된 뒤에 작업자가 뜹니다. |
| 특권 컨테이너 | 노드의 권한을 거의 그대로 갖는 컨테이너입니다. | Docker 데몬 사이드카가 해당합니다. 이 구성의 가장 큰 위험이고, 전용 노드에 올리는 것을 전제로 합니다. |
| ★ NetworkPolicy | 파드 사이의 통신을 허용 목록으로 제한하는 규칙입니다. | 들어오는 통신은 기본 차단입니다. 작업자는 DNS와 공인 주소만 나갈 수 있어서, 샌드박스 안의 코드가 API, 다른 파드, 메타데이터 주소에 닿지 못합니다. |
| 메타데이터 주소 | 클라우드에서 서버가 자기 자격 증명을 받아 가는 내부 주소(169.254.169.254)입니다. | 신뢰할 수 없는 코드가 여기에 닿으면 클라우드 권한을 훔칠 수 있어서 막습니다. |
| 프로브(probe) | 쿠버네티스가 파드에게 "살아 있는가, 받을 준비가 됐는가"를 묻는 검사입니다. | API의 `/api/health`를 씁니다. |
| PodDisruptionBudget | 노드 점검처럼 계획된 작업 때 한 번에 내려갈 수 있는 파드 수의 제한입니다. | API는 한 번에 하나만 내려갑니다. |
| kustomize, base, overlay, component | 같은 매니페스트를 환경마다 조금씩 다르게 쓰기 위한 도구입니다. base는 공통, overlay는 환경별 차이, component는 끼웠다 뺐다 하는 조각입니다. | `deploy/k8s/base`, `overlays/local`과 `multinode`, `components/{postgres,sandbox-dind,ingress,local-llm}`. |
| 온프레미스 | 클라우드가 아니라 사내망에 직접 설치해 운영하는 방식입니다. | 관리형 서비스 없이도 돌도록 PostgreSQL과 사내 LLM을 선택 조각으로 두었습니다. |
| 정적 서빙 | 미리 빌드한 HTML, JS, CSS를 그대로 내려 주는 방식입니다. | FastAPI가 React 빌드 결과를 내려 줍니다. 운영에 Node 서버가 없습니다(D31). |
| SSE | 서버가 연결을 열어 두고 한 방향으로 메시지를 보내는 방식입니다. | 분석 진행 로그입니다. 재생 모드는 `events.jsonl`을 다시 흘려 보냅니다. |

**스스로 확인:** 쿠버네티스 없이도 도는데 왜 쓰는가?
**답:** 기능 때문이 아니라 운영 때문입니다. 죽으면 다시 띄우고, 멈추지 않고 교체하고, 작업자를 늘리고, 신뢰할 수 없는 코드의 통신을 가두고, 비밀값을 컨테이너별로 나눠 줍니다. 한 팀이 서비스 몇 개를 쓰는 규모라면 한 대에 Compose로 올려도 충분합니다.

**스스로 확인:** 샌드박스를 쿠버네티스에서 돌릴 때 가장 큰 위험은 무엇인가?
**답:** Docker 데몬 사이드카가 특권 컨테이너라는 점입니다. 전용 노드에 올리고, 데몬은 파드 안에서만 듣게 하고, 작업자의 나가는 통신을 제한해 피해 범위를 줄였습니다. 특권 없이 격리하는 방식(gVisor, Kata)은 만들지 않았습니다.

## 11. 수치를 말할 때 주의

1. 일치율은 표본 크기와 함께 말합니다. 사람 라벨은 10 ~ 20건, 블라인드 세트는 45건과 47건입니다.
2. 첫 번째 블라인드 세트(47건)는 점수 조정에 쓴 자료입니다. 그 자료로 잰 수치는 검증이 아닙니다. 검증은 조정 뒤에 만든 두 번째 세트(45건)입니다.
3. 블라인드 세트의 정답은 사람이 아니라 별도 AI 세션이 만들었습니다.
4. 2단계 모드는 외부로 코드가 나가지 않는다는 것만 확인했습니다. 작은 로컬 모델(7B)의 판독 정확도는 낮았고 정답 라벨로 측정하지 않았습니다.
5. 쿠버네티스 구성은 k3s 3노드 시험 클러스터에서 확인했습니다. 실제 NFS, 관리형 DB 제품, 공인 인증서, 노드 장애는 확인하지 않았습니다.
6. 기존 도구와의 비교표(`docs/REQUIREMENTS.md` 3장)는 공식 문서로 다시 확인하지 않았습니다.
7. 수치의 출처는 `HARNESS.md` 7장의 날짜별 기록입니다. 말하려는 수치가 거기에 없으면 측정하지 않은 것입니다.
