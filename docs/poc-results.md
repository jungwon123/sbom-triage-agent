## 측정 범위와 한계

- 규칙 단계까지 측정했다. **LLM 에이전트는 실행하지 않았다** (API 키 없음).
- golden set을 라벨링하지 않아 **일치율과 NOW 누락은 미측정**이다. 버킷 분포는 정답률이 아니다.
- SBOM은 Syft 대신 lockfile 파싱으로 만들었다. Syft가 설치되어 있지 않다.
- CVSS는 v3 벡터로 계산했고 없으면 GHSA 등급 대표값을 썼다.
- 조치안은 사람이 작성했다. 재시도 사례도 에이전트가 아니라 사람이 수행했다.
- 샌드박스는 데모 레포만 측정했다. `--read-only`는 아직 적용하지 않았다.

## 설계에 준 영향

1. 조치 명령은 lockfile의 기존 버전을 제거하고, 조치 후 설치는 `npm install --ignore-scripts`로 한다.
2. 기본 조치 버전은 최소가 아니라 패키지의 가장 높은 수정 버전으로 한다.
3. `apply` 성공을 믿지 않고 재스캔으로 판정한다.
4. 테스트가 없거나 DB가 필요한 레포에서는 `verified`의 의미가 약하다. 판정과 별도로 **검증 강도**(테스트 실행 수)를 표시한다.
5. DB가 필요한 레포를 위해 컨테이너 내부 Mongo 같은 서비스 지원을 검토한다.
6. import 검색에서 주석과 문자열을 제외한다.

## 운영 PoC (2026-11-01)

운영 설계의 두 가정을 시험했다. 결과는 `out/poc/queue.json`, `out/poc/concurrency.jsonl`. 제품 코드에는 넣지 않았다.

**샌드박스 동시 실행.** `poc/concurrency_poc.py`. 같은 조치 작업 12건(realworld 6, NodeGoat 6)을 동시 1, 2, 4, 8, 12개로 2회씩 실행했다. 호스트 재스캔은 제외했다. Docker Desktop 12 CPU, 메모리 7.65GiB 환경이다.

| 동시 실행 | 분당 작업 (1회차 / 2회차) | 작업당 평균 초 | 최대 메모리 |
|---:|---:|---:|---:|
| 1 | 2.8 / 3.1 | 21.8 / 19.1 | 1.1GiB |
| 2 | 4.6 / 5.9 | 26.0 / 20.1 | 1.5GiB |
| 4 | 4.8 / 6.8 | 45.6 / 32.1 | 2.6GiB |
| 8 | 3.2 / 6.2 | 126.4 / 65.5 | 5.0GiB |
| 12 | 2.2 / 3.9 | 282.2 / 160.1 | 6.6GiB |

- 처리량은 동시 4개에서 최고였고 1개 대비 약 2.2배다. 8개부터 줄고 12개는 2개보다 낮다.
- 120건 전부 copy, apply, install, build가 통과했고 realworld 테스트 요약도 모든 실행에서 같았다. 동시 실행이 판정을 바꾸지 않았다.
- 네트워크를 쓰지 않는 test 단계도 함께 느려졌다(동시 1개 약 16초, 12개 73~137초). npm 네트워크만의 문제가 아니라 이 환경의 로컬 자원 경합으로 보이나, 디스크와 CPU 중 무엇인지는 측정하지 않았다.
- 회차 간 차이가 최대 2배로 크다. 1회차는 다른 작업과 겹쳤을 수 있다. 절대값이 아니라 꺾이는 모양만 믿는다.

**PostgreSQL 큐.** `poc/queue_poc.py`. PostgreSQL 16 임시 컨테이너, 작업은 sleep으로 모사했다.

| 시나리오 | 결과 |
|---|---|
| 빈 작업 2만 건, 워커 1 / 4 / 8개 | 초당 713 / 1,897 / 2,601건, 전부 완료, 같은 시도 중복 획득 0 |
| 작업 중 워커 SIGKILL (60건) | 유실 0. 죽은 워커의 작업 1건은 lease 만료 후 다른 워커가 완료 |
| 워커를 lease보다 오래 멈춘 뒤 재개 (30건) | 유실 0. 재개된 워커의 늦은 완료 1건을 fencing이 거절 |

- 작업은 at-least-once다. 위 두 장애에서 해당 작업이 2번 시작됐고, 완료는 한 번만 인정됐다.
- 큐 처리량은 샌드박스 처리량(초당 약 0.1건)보다 1만 배 이상 커서 DB가 먼저 막힐 가능성은 낮다.
- DB 자체의 장애, 복제, 백업은 시험하지 않았다. 운영 설계에서 PostgreSQL은 단일 장애점이다.

## 운영 설계에 준 영향

1. 샌드박스 워커는 서버당 동시 실행 수를 제한한다. 이 환경 기준 4개다. 서버 사양별로 다시 측정한다.
2. 처리량 확장은 동시 실행 수가 아니라 서버 추가로 한다.
3. 별도 메시지 브로커 없이 PostgreSQL을 큐로 쓴다.
